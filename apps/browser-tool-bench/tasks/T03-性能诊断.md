# T03 · 性能诊断：活动页为什么慢

- **测试维度**：性能 trace、诊断模型（对应文章第 4 节）
- **适用工具**：Chrome DevTools MCP（主角）、agent-browser、Playwright；@chrome 可作对照
- **靶场页面**：`/slow`

## Prompt（逐字使用）

> http://localhost:4399/slow 这个页面打开很慢。请帮我诊断：加载慢的主要原因有哪些？哪个因素对 LCP 影响最大？请给出证据（资源耗时、主线程任务等）。

## Ground Truth（三个故意埋的坑）

| 坑 | 数值 | 影响 |
| --- | --- | --- |
| `/assets/blocking.css` 服务端延迟 | 1200ms | 渲染阻塞 CSS，且按规范阻塞其后同步脚本执行，**对 LCP 影响最大** |
| `/assets/heavy.js` 同步长任务 | ~800ms | 主线程长任务（函数名 `crunchAnalytics`），在 CSS 返回后才开始执行，与之串联 |
| `/assets/hero.svg` 服务端延迟 | 1500ms | 耗时最长的单个资源，但**非阻塞且与上两者并行**，在首绘前已加载完，对 LCP 基本无影响（干扰项） |

> 修正记录（2026-06-12）：本卡最初把 hero.svg 写成"LCP 主因"，这是设计时的直觉错误。正式测试中 agent-browser 和 Chrome DevTools MCP 两个独立 Agent 用 trace 证据一致证明：渲染链为 blocking.css（~1205ms TTFB）→ heavy.js（~804ms 长任务）串行，LCP ≈ 2.1-2.4s，LCP 元素是文本段落；hero.svg 并行加载、首绘前完成，是"看起来最慢但不背锅"的干扰项。靶场反而因此多了一层考点：会不会被最慢资源带偏。

## 判定标准

| 等级 | 条件 |
| --- | --- |
| ✅ 成功 | 指出 blocking.css 是 LCP 主因、heavy.js 长任务次之，给出耗时证据；能识别 hero.svg 是干扰项更佳 |
| ⚠️ 部分 | 找到坑但归因错误（如把 hero.svg 当主因），或只给笼统结论没有定位到具体资源 |
| ❌ 失败 | 无法给出任何带证据的结论 |

## 记录指标

轮数 / token / 时间；额外记录"结论是工具直接给的 insight，还是 Agent 自己从原始数据推的"。

## 预期差异点

文章断言 DevTools MCP 的 `performance_start_trace` + `performance_analyze_insight` 应该最省事；agent-browser/Playwright 要靠读 Performance API 和请求时序自己推理——验证诊断质量和 token 成本差多少。
