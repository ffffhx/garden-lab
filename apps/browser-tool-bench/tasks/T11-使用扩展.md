# T11 · 使用扩展：通过设置页改写徽标文字

- **测试维度**：`chrome-extension://` 页面的可达性、扩展页内的表单操作、跨上下文生效验证（对应文章第 6 节"扩展安全域"；与 T09 的区别：T09 测**开发调试**扩展，本卡测**使用**扩展的功能）
- **适用工具**：agent-browser、Chrome DevTools MCP、playwright-cli；@chrome / @browser 作对照（验证产品是否封装了扩展页访问）；bb-browser 待 click 修复后再测
- **边界预测**（按"协议层 / 封装范围 / 安全策略"公式）：扩展的 options 页是独立的 `chrome-extension://<id>/options.html` CDP target——协议层人人可达，胜负应该出在封装范围（工具能不能枚举/打开扩展 target）

## 前置准备

1. 被测工具控制的浏览器必须以**有头模式**运行，且已加载 `extension-sample/`。
2. ⚠️ **加载方式的坑（2026-06-13 实测）**：正式版 Google Chrome 137+ 会**静默忽略** `--load-extension` 启动参数（本机 Chrome 149 实测复现：参数在进程命令行里、chrome://extensions 里却没有扩展）。可靠的装载方式按优先级：
   - Playwright `launchPersistentContext` + `--disable-extensions-except/--load-extension`（Chrome for Testing，已验证全链路可用）；
   - Chromium / Chrome for Testing 手动启动加同样参数（注意 CfT 冷启动 DevTools 端口就绪可能要 10s+）；
   - 正式版 Chrome：只能在 chrome://extensions 开发者模式下人工"加载已解压的扩展程序"。
3. 打开 http://localhost:4399/ 确认右下角显示默认徽标「BENCH EXT v1.0.0」。
4. **每轮测试后复位**：在扩展设置页清空文字保存，或删除浏览器 profile 中该扩展的 storage（最干净的方式：删 profile 重新装载）。

> Ground truth 已于 2026-06-13 用 Playwright persistent context 全链路验证：默认徽标 `BENCH EXT v1.0.0` → chrome://extensions 可读到扩展 ID（Playwright 选择器穿透 shadow DOM）→ options 页保存提示语逐字匹配 → 刷新后徽标 `HELLO-2026 · v1.0.0`。

## Prompt（逐字使用）

> 当前浏览器里装了一个叫 Bench Badge 的扩展。请打开它的设置页，把徽标文字改成 HELLO-2026 并保存，然后打开 http://localhost:4399/ ，确认页面右下角的徽标文字已经变成 HELLO-2026，把你看到的徽标完整内容告诉我。

## Ground Truth

- 设置页路径：`chrome-extension://<扩展ID>/options.html`（ID 由加载路径派生，**Agent 需要自己发现**——通过 `chrome://extensions`、扩展管理 API 或枚举 CDP targets，这本身是考点的一部分）。
- 设置页内：输入框 `#badge-text` 填入 `HELLO-2026` → 点「保存」→ 状态栏显示「已保存：徽标文字将显示为「HELLO-2026」（刷新靶场页面生效）」。
- 刷新/打开靶场页面后，右下角徽标（`#bench-ext-badge`）显示：**`HELLO-2026 · v1.0.0`**。

## 判定标准

| 等级 | 条件 |
| --- | --- |
| ✅ 成功 | 通过设置页 UI 完成修改，且在靶场页面验证徽标为 `HELLO-2026 · v1.0.0` |
| ⚠️ 部分 | 改成功但未验证；或绕过设置页 UI（如附加到扩展 target 直接 eval 写 `chrome.storage`）——证明了 target 可达但没走用户路径 |
| ❌ 失败 | 无法到达 `chrome-extension://` 页面，或找不到扩展 ID |

注意：在**靶场页面**的 Runtime 里 eval 是写不了 `chrome.storage` 的（页面世界没有 chrome.* API），所以这道题没有廉价的 eval 旁路——逃生舱要起作用，至少得先附加到扩展自己的 target，而这正是本卡要测的能力。

## 记录指标

轮数 / token / 时间 / 打断次数；额外记录两项——
1. **扩展 ID 的发现路径**（chrome://extensions 页面、扩展管理 API、还是 CDP target 列表）；
2. 设置页是否出现在工具的 tab/target 列表里（衡量"扩展页对该工具是否一等公民"）。

## 预期差异点

- agent-browser：理论上 `tab` 能列出 chrome-extension:// target，`open chrome://extensions` 也可达——验证 Electron 轮发现的"connect 会话模式 target 枚举问题"是否在扩展页上重演。
- Chrome DevTools MCP：新版本带扩展工具类（list/reload/触发 action），看它是否覆盖 options 页的打开与操作。
- playwright-cli：Playwright 库支持扩展测试（persistent context），但 CLI 的 attach 限制是否挡住扩展 target 是未知数——这是它继"只能 attach 自家浏览器"之后第二个待验证的边界。
- @chrome / @browser：产品没封装扩展页访问的话应为 ❌，但它们本身就是扩展，值得观察报错形态。
