## 2. 重点业务需求

## 2.1 商业化权益能力建设

分为 2.0 与 3.0 两个版本。

### 2.1.1 商业化权益 2.0

![扣子编程部署页：构建次数达上限时，在「开始部署」入口弹出升级提示](figure-01-deploy.png)

![项目管理里不同套餐的权益项展示，额度来源和拦截表现并不统一](figure-02-benefits.png)

#### 背景

随着扣子进入商业化阶段，需要对某些能力进行权益项拦截。简单说就是用户使用某个权限不足的功能时，引导其跳转到付费墙弹窗，并高亮对应权益项。

#### 问题与挑战

**权益表现不统一。** 比如 QPM 相关只展示上限，前端不会做拦截；日志相关则根据使用率不同会有不同交互。

**权益项分散。** 套餐额度来自商业化后端接口，用量来自各个业务方后端接口，需要跟多个后端对齐。

#### 思考与方案

通过场景 Hook 聚合两类数据：商业化套餐权益，以及业务后端使用量。每个权益都封装一个单独的权益判断 hook，从商业化和各个业务方后端分别调用接口拿数据。

**商业化权益 2.0 前端接入架构：**

![权益 2.0：套餐接口进入 Benefits Store，再和业务用量一起交给各权益 hook 判断](figure-wb-04-benefits-2-flow.jpg)

#### 成果

完成 6 类编程权益拦截。

### 2.1.2 商业化权益 3.0

![权益 3.0 拦截弹窗：权限不足时先提醒升级，再进入支付流程](figure-03-paywall.png)

#### 背景

进入 3.0 后，权益项骤增，不能再跟 2.0 一样分开处理，需要一个统一方案，且要支持移动端复用。权益拦截链路交互改为：用户使用某个权限不足的功能前，会弹出拦截弹窗提醒升级；如果用户升级，再弹出对应支付弹窗，引导完成后续支付。

#### 问题与挑战

**Space、Coding、移动端三端复用，还要适配未来新增权益项。** 三端都有同样的功能，要避免重复实现。2.0 的权益拦截当时就是我在负责，那时权益项不多，每个权益项都在业务侧单独处理，比较混乱，PC 和移动端还重复实现。3.0 权益项骤增，需要一套统一、可复用的权益拦截方案。

**升级套餐的推荐有多种逻辑。** 往上取一档不一定能满足用户新增的用量；个人版、团队版、企业版权益类型不同、表现不同，要分别处理，还要兼容历史老套餐和未来新增套餐。

**需求多且分散。** 商业化部分没有单独拆分需求，具体拦截逻辑分散在 8 个业务需求内，需要逐一参与完整评审链路，并关注其中与商业化有关的部分。

**商业化后端接口无法提供扩容相关信息。** 这类权益在不同用户上的表现不统一，需要由对应业务方后端单独提供接口并自行处理，商业化侧只负责统一收口。

#### 思考与方案

拆分业务逻辑与 UI，抽象权益拦截、套餐推导能力，供 PC 端和移动端使用。不依赖页面和 UI，可以被 Space、Coding、移动端直接复用。

收敛为统一业务链路，调用方只需要传入权益类型和本次新增量，其余逻辑由商业化侧处理：权益可用则继续原操作，不可用时走商业化提供的这些能力。商业化侧集中处理权益文案，以及后续的支付链路。

**抽象权益拦截能力与套餐推导能力：**

![左侧是统一权益判断，右侧是历史套餐映射与额度匹配的套餐推导](figure-wb-01-benefits-capability.jpg)

**统一权益拦截业务链路（端到端时序）：**

![调用方只传权益类型和新增量，商业化侧完成判断、套餐推导、拦截弹窗和支付](figure-wb-05-benefits-3-seq.jpg)

#### 后期优化点

后续计划将权益弹窗文案改造成运营可配置能力，并作为一次全栈实践：由运营维护展示文案，后端提供配置的保存与读取接口，前端再根据权益和使用场景动态消费。这块业务逻辑相对清晰，团队也在推动全栈能力建设，我准备把它作为一次全栈实践，打通从运营配置到用户侧展示的完整闭环。

#### 成果

已为 25 个权益项配置专属付费墙。覆盖算力与 Agent、模型与视频、协作配额、部署与安全四类场景。对应需求仍留在 Meego，这里只保留原链接，不另转成文章：

## 2.2 扣子编程：部署 Trace 与分析

![部署 Trace：对话侧的一次生成，对应到 Trace ID、Token 和输入输出](figure-04-trace.png)

![部署后的分析页：用户活跃、留存和代码侧的 Agent 运行结果](figure-05-analytics.png)

#### 背景

入职第一周接触的第一个业务需求。

#### 问题与挑战

**业务和代码都不熟悉。** 需要快速理解部署流程、Trace 数据结构和仓库已有能力。

**对 AI 编程的认识还不够成熟，实践还不够多。** 在校期间受预算不足等原因，用不起当时最新最好的模型，相关 AI 实践也不够丰富。

#### 思考与方案

先借助 AI 了解项目架构以及我所开发部分的业务逻辑：页面对应的代码在哪里，这个页面的 URL 是什么，应该在哪里开发这些东西。

采用类似 Spec Driven 的方式进行开发。相比在校期间的 Vibe 与传统手写，spec + SOTA 模型给这次开发提高了不少效率。

#### 成果

完成了第一个需求的完整交付。

加深了对 AI 的了解与实践，开始积极使用市面上最新的模型，主动给 AI 提供上下文与工具。我也逐渐去研究如何购买 Claude Code、Codex，并学着主动给 Agent 提供和建设更丰富的上下文与工具。

#### 收获与思考

随着自己不断使用 AI，发现这种 Spec Driven 范式并不适合自己。实际开发体验里，Spec 主要有这些问题：

1. **Spec 文档过期非常快。** 同事在提交代码、需求在变化，文档写完即过时。对 Agent 来说，过期文档就是毒药。
2. **SDD 生成的文档（proposal、design、tasks）信息密度极低。** 同一件事翻来覆去说。不认真 review 就成了 vibe；认真 review，人脑就成了瓶颈。动不动几百上千行，根本 review 不过来。
3. **Spec 制造「文档即完成」的幻觉。** Agent 真正遇到的问题往往是 spec 里没有的，比如接口变了、状态存储位置变了。很多东西只有通过运行系统才能知道。

现在我的开发方式，可以概括为下面几步：

1. **需求、技术方案大概对齐（80%）。** 先和 Agent 把需求背景、我负责的范围以及需求中模糊的地方对齐，减少双方误解；把技术方案和架构聊清楚，比如哪些部分可以复用，哪些需要重新开发，应该放到哪个 package。
2. **建立验收标准，提供验收工具。** 把关键交互聊清楚，然后提供切换账号、mock 等工具，让 Agent 自行去验收。
3. **拆分需求。** 如果需求比较大，会拆成多个任务 / Session，每个任务一个 Session，再让主 Session 去控制子 Session，随时能看到子需求进度。
4. **Agent 自由发挥。** 允许 Agent 结合当前代码库、各种飞书文档，自主完成编码以及验证。
5. **人工验证并调整，不断小步迭代。** Agent 完成测试之后，我会手动走一遍研发自测；有问题的地方，会和 Agent 讨论后再改。

简单来说：把需求、方案、验收标准聊清楚，中间怎么做，全部交给 Agent。

这些都是我自己的实践与探索。新模型出来之后，这套方案可能也就成了落后的方法。我觉得最重要的还是多练，积极使用 SOTA 模型，以及养成任何问题先跟 Agent 聊的习惯。

## 2.3 扣子商业化：套餐升降配与订阅管理优化

![套餐页：个人免费 / 进阶 / 高阶 / 旗舰，订阅周期和附加权益都不一样](figure-06-plans.png)

![订阅管理：当前套餐、可切换选项和购买记录](figure-07-subscription.png)

#### 背景

用户会有升配、降配或切换套餐的需求。旧版本升降平配的用户表现混乱。这次优化想为用户提供一致、可预期的决策体验。

#### 问题与挑战

**规则维度多，共计 47 条，业务逻辑复杂。** 原订阅渠道、目标订阅渠道、购买周期、原套餐版本、目标套餐版本等共同决定用户能否变更以及何时生效。

**账号难构造、规则组合多，导致测试成本极高。** 一是很难构造账号，比如要求原套餐是苹果订阅、原套餐是 CRM 订阅；二是组合太多，很多账号测过一次之后订阅状态变化，无法再次使用；再加上 A/B 实验，复杂度翻倍。

![个人版和团队版的套餐变更规则树：升 / 平 / 降 × 订阅渠道 × 周期](figure-wb-02-subscription-rules.jpg)

#### 思考与方案

借助 AI 理清业务逻辑，按升、降、平三大类划分用户表现。多套餐时，收敛为「待生效」与「生效中」两个大类。前端交互上给用户分成 3 大类，每类走不同的弹窗流程。

开发联调时，先 Mock 指定响应字段进行预览，并把 Mock 数据保存以供复用：让 AI 去 Mock 指定接口的指定字段，然后作为一条规则沉淀下来，方便后续开发和测试。

#### 收获与思考

理清了套餐升降配与订阅管理优化相关的业务逻辑。后续开发和评审这块需求时，更加得心应手。

## 3. 技术建设

## 3.1 商业化域代码组织结构重构

#### 背景

商业化能力长期分散在一个历史遗留的业务包目录下（`packages/studio`），和多个不相干业务包混在一起，依赖关系混乱，缺少共同父域，没有统一对外出口。推动并实施商业化域重构，希望在不停止业务迭代的前提下，将商业化代码组织为可维护的领域结构，并为非商业化业务提供稳定出口。

#### 问题与挑战

**依赖方向已经倒置。** 本应位于底层的 `subscription-common` 反向依赖 UI 层 `subscription-paywall`，新增能力很难判断应该落在哪一层。

**出口不稳定，某些能力存在多个可用入口。** 业务方为了复用局部 Hook 或组件，只能深路径引用旧包内部文件。目录一旦调整，外部调用方就被迫跟着迁移。

**公共能力分散，缺少统一管理。** 付费墙导航等能被多个入口共同使用，却没有清晰的共享层，导致 UI、领域逻辑和页面编排互相渗透。

**迁移规模大且代码持续变化。** 共涉及 518 个逻辑变更文件；迁移期间 master 仍不断加入商业化需求。需要处理重命名、依赖修正、导出兼容、锁文件与构建，同时保证线上功能和产物体积不明显回退。

**测试困难。** 因为各种依赖倒置，需要重新编排，可能涉及逻辑修改。牵扯范围比较大，测试比较麻烦。

#### 思考与方案

Feature-first + 分层依赖约束的混合架构：把一个业务的代码集中在一起，把公共逻辑提出来，避免重复实现，并建立 entry 层，将内部实现与外部引用解耦。

明确依赖顺序：依赖方向固定为上层依赖下层，禁止反向依赖，并配备 eslint 规则约束。

只导出必要 API，非商业化业务只能从 entry 引用。entry 层刻意不提供 root export，也不提供 `export *` 通配导出。这样内部结构可以继续演进，外部依赖保持稳定。

按迁移批次控制风险。先建立新目录和依赖边界，再迁移共享基座，最后迁移业务流程，随后逐步修改调用方并清空旧包。

Agent 跑 P0、P1 中核心且不涉及支付的测试用例，支付部分人工测试。

**架构图：commercial 分层架构与依赖方向**

![外部包只走 commercial entry；向下是 feature / shared / core 的单向依赖](figure-wb-03-commercial-arch.jpg)

#### 后期优化点

继续把移动端商业化逻辑收束到同一领域模型，减少 Web 与 App 各自维护套餐和权益规则。

#### 成果

建立统一商业化代码域，本次迁移共计覆盖 518 个逻辑变更文件。将分散在各业务包中的商业化能力收拢到 `packages/commercial`，落地 6 个职责清晰的子包，形成 core、shared、feature、entry 4 层单向依赖结构。

稳定出口已在业务中实际落地，提供 88 个对外 API，形成 334 处引用，覆盖 8 类商业化能力。

#### 收获与思考

有了 AI 之后，代码迁移变得容易。难的是代码架构的设计，以及迁移之后的测试。

## 3.2 Coze 账号切换工具链

![账号切换插件：在已登录页面上选择目标账号并一键切换](figure-08-account-switch.gif)

#### 背景

商业化功能验证需要频繁切换套餐。过去通常先查表找账号，退出当前账号、重新登录；单次操作往往超过 2 分钟。

#### 问题与挑战

**环境和账号复杂。** 需要适配 PC 端、H5，主账号、子账号等不同情况。

**账号和 Session 属于高敏感数据，需要权限校验。** 只能 Coze 内部人员使用。

**需要支持 Agent 和人共同使用。** Agent 在测试需求时，经常会有切换账号的动作。

#### 思考与方案

方案经历了三次迭代。

**第一版：通过模拟点击完成账号切换，缺点是不稳定且慢。** 工具使用 Playwright 驱动 Coze 登录页面，自动填写账号并点击登录、退出。遇到页面改版时容易中断，稳定性不足，速度较慢。

**第二版：通过调用登录、退出接口完成账号切换，缺点是无法支持企业版主账号。** 为减少 UI 变化的影响，工具改为在页面上下文中直接调用登录、退出接口。接口方案缩短了操作链路，也避开了大部分模拟点击，但需处理反爬签名；切换企业版主账号时需要手机号验证，接口无法直接绕过。

**最终版本：获取目标账号 Session，并替换目标环境中唯一的 Coze Session Cookie。** 从测试那边了解到有拿 UID 换 Session 的服务。客户端只替换目标环境中唯一的 Coze Session Cookie，变得更简单更稳定。切回自己账号时，通过 tab 跳转替代模拟点击，并追加 `prompt=none`，复用该 Profile 的飞书登录态完成登录。

**权限校验。** 通过字节云确认用户为字节员工，再通过 Kani 确认用户为 Coze 员工，权限校验通过之后才可以使用。

## 3.3 通用 AI 工程化：ProfilePilot

![ProfilePilot：给多个隔离 Profile 分配端口、同步登录态，并查看 Agent 占用](figure-09-profilepilot.png)

![真实页面上的 Agent 控制条：任务进行中可暂停、继续，人和 Agent 不抢同一个窗口](figure-10-agent-overlay.png)

工具作用：复制多个有相同登录态和插件的 Profile，给每个 Agent Session 都配备一个有专属 proxy 的 Profile，互不干扰。

#### 背景

权益、升降配、付费墙验收，必须用真实登录态让 Agent 点页面；支付部分则必须手动完成。于是研究了市面上六种 Agent 浏览器工具，并对它们做了多维度（时间、token 消耗、能力边界）的评测。评测原文仍留在内部 Wiki，这里只保留链接，不转载：[Agent浏览器控制工具测评](https://bytedance.larkoffice.com/wiki/WnC9wLmOcieH50kHWBocrexUnmf)。共同缺口就是处理不了：人和 Agent 抢同一个 Chrome，以及 Agent 抢焦点。

#### 问题与挑战

**Agent Session 和 Profile 之间需要建立连接。** 每个 Agent 需要使用单独的 Profile；具体哪些 Profile 可用，需要被 Agent 感知到。

**用户需要感知到浏览器控制权的变化。** 用户可能随时自己点击页面、接管窗口或者要求暂停，需要平滑切换，且切换过程中不能丢掉上下文。

#### 思考与方案

**Gateway 统一分配 Profile，并管理控制权。** Gateway 先检查目标 Profile 是否空闲，并立即分配给当前 Session。如果目标 Profile 已被占用，Gateway 自动选择其他空闲 Profile；没有可用 Profile 时停止执行。Profile 的占用、用户接管、控制权交还和任务结束，都以 Gateway 的状态为准。

**Wrapper 负责接入，daemon 负责持续连接。** Wrapper 负责解析命令、向 Gateway 申请 Profile 和 Ticket；agent-browser daemon 使用 Ticket 与 Gateway 建立 WebSocket。后续 CDP 命令统一经过 Gateway 校验，再通过专用管道转发给 Chrome，Chrome 本身不开放调试端口。

**一次任务的连接流程（Session 注入 → 查注册表 → 租约 → Ticket → 受控转发）：**

![Agent 不带 --session 发命令，由 Gateway 原子绑定 Profile 并签发一次性 Ticket](figure-wb-07-profilepilot-seq.jpg)

#### 后期优化点

分享 ProfilePilot 给组里其他同学使用，吸取组里其他同学的意见。通过组内分享让更多人了解它在「账号 / 登录态隔离、用户与 Agent 互不抢占、Agent 操作可见可接管」上的价值，收集真实场景需求。

#### 成果

日常稳定并行 3 个 Agent 浏览器 Session，多个需求同时开发和验收。

#### 收获与思考

对浏览器以及浏览器控制工具相关的 skill、CLI 有了更深入的了解。

## 5. 反思与成长

**写代码可能是相对简单的一环，难的是沟通以及上下文的对齐。** 很多需求的复杂度不在写代码本身。比如 Coze 商业化权益拦截的建设，写代码占了比较少的时间，更多时间花在参加各种评审拿到准确物料、和 PM 对齐权益整合、和业务方讲清商业化的能力边界——哪些是我们统一收口的，哪些（比如扩容）必须业务方后端自己实现。让各方对齐，比把代码写对更关键，也更难。

**快速演进的 AI 时代，不断学习、尝试新模型很重要。** 三个月前的文章可能会变得毫无意义，今天的最佳实践可能很快过时。我觉得很难依靠一套固定的规范长期拉齐能力。使用最新的模型和 Agent 去不断探索、尝试，寻找当下最适合自己的协作方式，是非常重要的。

**AI 时代，学习重心变了，保持理解、注意力、判断变得更加重要。** 23 年 9 月份接触前端那会儿，学的是各种语言的语法和 API 的用法，比如 let 和 const 的区别，不会这些就写不了代码。现在我觉得这些不重要了，不会也没关系。现在真正稀缺的是保持理解、注意力和判断，不然 AI 只是更快地把我们带向错误方向。AI 可以帮你思考很多方案，但人要知道目标是否值得做，哪种方案是否更优。

## 6. 未来规划

**补齐全栈能力，完成业务闭环。** 未来业务需求会更强调全链路交付。后面会着重了解服务端开发流程，并在真实需求中亲自完成从方案设计、接口开发到上线验证的完整链路，逐步具备独立交付全栈业务的能力。

**围绕商业化主链路建立系统领域认知。** 把权益、订阅、积分在代码之外的隐性规则补齐为 skill 以及 `AGENTS.md`，降低 Agent 理解商业化的门槛；定制 mock 场景，降低测试难度。

**持续去使用最新的模型和 Agent，不断探索 AI 的能力边界。** 模型训练分布内的东西表现得像专家，分布外的东西即使人类觉得很简单，它也会出错。不能因为 AI 在代码上很强，就觉得 AI 在工程判断上都很强。
