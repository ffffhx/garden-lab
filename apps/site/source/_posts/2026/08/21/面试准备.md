## 2. 字节跳动·扣子实习

### 2.1 商业化权益能力建设

**背景：**

扣子进入商业化阶段后，需要在用户使用受限功能时进行权益拦截与付费引导。

**难点：**

1. **三端复用与扩展性**：Space、Coding 以及移动端存在相同的权益功能，如果继续在业务侧各自实现，会导致严重的逻辑冗余与维护成本；
2. **多维度的套餐推导逻辑**：单纯向上一档推荐往往无法满足用户新增的用量需求；个人版、团队版与企业版的权益形态各异，且必须向前兼容历史老套餐、向后兼容未来新增套餐；
3. **需求分散与链路协同**：商业化逻辑分散在 8 个具体的业务需求之中，且部分扩容信息无法由商业化后端统一提供，需要各业务方后端提供独立接口并在前端收口。

架构方案：

- **抽象出独立的能力**：统一的「权益拦截判断」与「套餐推导规则」，不依赖任何特定页面 UI，可直接供 PC 端、移动端多场景复用；
- **统一步骤调用契约**：调用方只需传入权益类型与本次操作的新增用量，后续的拦截判定、推荐套餐推导、付费墙文案组装及支付跳转全流程均由商业化统一处理。

![左侧是统一权益判断，右侧是历史套餐映射与额度匹配的套餐推导](./面试准备/figure-wb-01-benefits-capability.jpg)

#### 商业化权益能力架构（文字版）

图中将能力拆成两个独立部分：左侧判断当前权益是否足够，右侧推导需要推荐的目标套餐。两部分只处理权益数据与规则，业务页面通过统一契约调用。

**左侧：统一权益判断。**

1. **输入业务上下文**：接收权益类型 `benefitType`、当前套餐权益数据 `benefits`、当前使用量 `currentCount` 和本次新增量 `requestedAddCount`。
2. **计算本次操作所需总量**：`requiredTotal = currentCount + requestedAddCount`，再与当前套餐中对应权益的额度比较。
3. **返回判断结果**：若 `requiredTotal ≤ 当前套餐权益额度`，返回权益可用，调用方放行并继续原业务操作；否则返回权益不足，进入后续拦截与套餐推荐流程。

**右侧：套餐推导。**

1. **输入推荐参数**：接收当前套餐等级 `currentLevel`、各套餐的权益信息 `benefitTypeInfos` 和本次新增量 `requestedAddCount`，首先判断当前套餐是否属于历史套餐。
2. **历史套餐走固定迁移映射**：不走普通的逐档筛选。`V1Pro` 和 `ProPersonal` 迁移到 `PersonalAdvanced`，`Team` 迁移到 `EnterpriseBasic`，`Enterprise` 迁移到 `EnterprisePro`。
3. **非历史套餐按额度筛选**：先筛选与当前套餐属于同一套餐族、且等级更高的候选项，再按图中的规则检查 `候选套餐额度 ≥ 当前套餐额度 + 本次所需额度`，从满足条件的候选中选择最低匹配档位。
4. **输出推荐结果**：返回目标套餐等级 `targetLevel`；没有匹配套餐时返回 `undefined`，表示当前规则下没有可推荐的目标套餐。

这里有两个不同的计算基准：左侧判断操作能否执行，用的是“当前使用量 + 本次新增量”；右侧图示的非历史套餐推荐规则，用的是“当前套餐额度 + 本次所需额度”。前者回答当前权益是否够用，后者回答应推荐哪个升级档位。

#### 商业化权益 3.0 时序图

- **完整交互时序链路**：
  1. **触发拦截入口**：用户在业务界面中点击触发受权益管控的操作（例如新增协作者数量）；
  2. **契约化调用**：调用方调用商业化统一 Hook/方法 `useBenefitCheck(权益类型, 本次新增量, 当前使用量)`，只声明业务意图，不感知具体付费规则与套餐形态；
  3. **查询权益基准**：商业化侧向商业化后端发起请求，获取当前用户或企业主体生效的套餐等级、权益策略与额度上限；
  4. **返回套餐权益**：商业化后端返回最新套餐与权益元数据；
  5. **统一权益计算**：商业化侧在端侧执行统一判定公式：`当前使用量 + 本次新增量 ≤ 权益额度`，进入条件分支：
    - **分支 A [权益可用 · 未达上限]**：
    1. 商业化侧向调用方返回权益可用状态；
    2. 调用方放行操作，用户继续正常执行原业务流程。
    权益不足 · 拦截与动态推荐]**：
    3. **智能套餐推导**：商业化侧根据额度缺口，自动向后推导并推荐能满足本次新增量的目标套餐（避免盲目向上一档推荐导致升级后额度依然不足）；
    4. **弹出统一付费墙**：商业化侧直接唤起全局统一的权益拦截弹窗（拦截文案、权益对比均由商业化域集中管控配置）；
    5. **用户确认升级**：用户查看权益对比后在弹窗内点击确认升级；
    6. **唤起收银台支付**：商业化侧弹出专属支付弹窗，引导用户完成下单与支付；
    7. **支付回调与额度同步**：用户完成支付后，商业化侧接收支付成功回调，向商业化后端请求刷新并重新同步最新生效的权益额度；
    8. **放行并恢复业务**：商业化侧通知调用方权益已生效，调用方继续执行（或自动重试）用户最初触发的原操作。
      > **扩容类权益设计约束**：针对按量扩容类权益，其可用性由具体业务方后端自主判断，商业化侧仅收口统一的拦截弹窗与支付收银台流程，保持核心职责清晰。

### 2.2 开发工作流的探索

这是我入职第一周独立接手的第一个业务需求。

刚入职时，面对完全陌生的业务背景与代码库，我经历了人机协同方式的探索与转变：

起初我尝试过规范化的 Spec-Driven 开发模式，但在实际高频迭代中很快发现了其局限性：

- **Spec 文档极易过时**：业务需求在变、同事在合入代码，文档写完即脱离真实上下文，而过期的文档对 Agent 是严重干扰；
- **文档冗余且信息密度偏低**：生成的 Proposal、Design 和 Tasks 动辄上千行，人工逐行 Review 容易成为效率瓶颈；
- **产生「文档即交付」的错觉**：真正的集成问题（接口参数变动、存储时机差异）往往只有在真实运行时才能暴露。

在此之后，我调整了人机协同的工作流，形成了更加实用的协作闭环：

1. **方案与范围对齐（~80%）**：先与 Agent 对齐需求背景、职责边界和架构设计（哪些复用、哪些新建、归属哪个 Package）；
2. **定义验收标准并提供工具**：聊清核心交互流程，配备切换账号、数据 Mock 等工具让 Agent 自主执行验证；
3. **大任务拆分子会话**：复杂需求按模块拆分为多个独立 Session，主 Session 负责推进进度与统筹；
4. **自主编码与小步验证**：Agent 结合现有代码库与相关文档自主完成编码与自测，最后由人工进行兜底验证与微调。

### 2.3 商业化域代码组织结构重构

商业化能力最初分散在历史遗留包中，与大量非商业化代码混杂在一起，逐渐积累了严重的架构问题：

- **依赖方向倒置**：本应作为底层基础的 `subscription-common` 反向依赖了上层 UI 包 `subscription-paywall`；
- **缺乏统一对外出口**：外部业务方为了复用部分能力，不得不深路径引用内部实现文件；
- **公共能力缺乏收口**：付费墙导航等基础能力在各处被随意拼装，UI、领域逻辑和页面编排深度耦合。

![外部包只走 commercial entry；向下是 feature / shared / core 的单向依赖](./面试准备/figure-wb-03-commercial-arch.jpg)

#### 商业化域分层架构（文字版）

这张图描述的是代码包的导入与重导出关系，整体方向为“外部调用方 → 统一入口 → 业务功能层 → 共享层 → 核心层”。其中业务功能层也可以直接依赖核心层，入口可以直接重导出受控的核心 API。

1. **外部调用方**：`apps coze coding`、其他应用与包，以及非商业化域的 `studio layout`、`studio home`、`studio setup`，统一从 `commercial entry` 导入商业化能力，不直接引用内部实现路径。
2. **Entry：统一对外入口**：`commercial entry` 集中重导出需要开放的 API。图中入口分别连接订阅、付费墙、活动三个 Feature，以及底层 Core，使调用方通过一个稳定出口使用不同层的能力。
3. **Feature：按业务功能组织**：`feature subscription`、`feature paywall`、`feature activity` 分别承载订阅、付费墙与活动功能。三个 Feature 都可以使用 `commercial shared` 的公共能力，也可以直接使用 `commercial core` 的底层能力；图中没有 Feature 之间的相互依赖。
4. **Shared：跨功能共享能力**：`commercial shared` 收纳多个 Feature 复用的能力，并向下依赖 `commercial core`。它不反向依赖订阅、付费墙或活动等上层 Feature，避免再次形成“公共包依赖具体业务 UI”的倒置关系。
5. **Core：底层核心能力**：`commercial core` 位于依赖链底部，为 Shared 和各 Feature 提供基础能力，不反向依赖 Shared、Feature 或 Entry。

图中的 `imports` 表示外部调用方导入统一入口，`re exports` 表示入口转出受控 API，`uses` 表示内部包使用下层能力。ESLint 依赖规则负责约束这些方向，防止业务代码绕过入口或重新引入反向依赖。

我们确立了 **Feature-first + 分层依赖约束** 的架构方案：

1. **清晰的 4 层单向依赖结构**：自底向上划分为 `core`、`shared`、`feature`、`entry`，严格禁止跨层反向依赖，并配置 ESLint 规则进行自动化卡口；
2. **受控的对外出口（Entry）**：仅对外暴露经过抽象的 88 个 API，刻意杜绝 `export *` 通配导出，确保内部实现能够持续演进而不影响外部依赖；
3. **分批次平稳迁移**：先搭建新目录结构与依赖边界，再迁移共享基座，随后迁移核心业务流程，最后分批替换业务方引用并清理旧包。

本次重构共覆盖 **518 个逻辑变更文件**，收拢落地为 6 个子包，在业务高速迭代的同时实现了零故障平滑过渡。

### 2.4 Coze 测试账号切换工具链

在商业化开发与验证过程中，经常需要在不同权限与套餐的测试账号之间切换。过去依赖查表找账号、退出并重新登录，单次操作耗时通常在 2 分钟以上。

为了兼顾开发效率与安全性，工具链经历了三代方案演进：

- **第一代（Playwright 模拟点击）**：自动填写账号密码并点击界面，但遇到 UI 结构调整时极易失效，耗时且不稳定；
- **第二代（直接调用登录/退出接口）**：绕过了大部分 UI 交互，但需额外处理反爬动态签名，且遇到需要短信验证的企业主账号时无法直接完成；
- **第三代（UID 换取 Session Cookie 替换）**：通过后端服务直接使用目标 UID 换取合法 Session 并注入当前环境，大幅简化了操作链路；切回本人账号时，通过带有 `prompt=none` 参数的 Tab 跳转静默复用飞书登录态。

同时，工具链通过字节云与 Kani 实现了双重身份校验，确保测试账号与敏感 Session 的访问安全，并提供了 Chrome 插件与 CLI 双入口，完美支持人和 Agent 共同调用。

#### 账号切换工具链完整时序与交互流程

上述时序图梳理了工具链运行过程中的 7 个核心参与方以及「鉴权获取业务 Token」与「账号切换双路径」两大核心阶段：

- **阶段一：获取业务 Token（首次登录 / Token 失效时）**：
  1. **发起鉴权**：用户或 Agent 在 Chrome 插件中点击发起鉴权；
  2. **请求鉴权**：Chrome 插件向 Stone (插件后端)发送鉴权请求；
  3. **OAuth 授权重定向**：Stone 将请求重定向至 ByteCloud OAuth 授权中心；
  4. **弹出授权确认**：ByteCloud OAuth 向用户展示 OAuth 授权界面或确认提示；
  5. **确认授权**：用户使用企业员工账号确认授权；
  6. **返回身份凭证**：ByteCloud OAuth 向 Stone 返回员工身份凭证（OAuth Code 或 Token）；
  7. **校验业务权限**：Stone 向 Kani 权限服务发起请求，严格校验该员工在 Coze 内部的业务与项目权限；
  8. **鉴权通过**：Kani 确认该员工具备对应项目权限，向 Stone 前端返回通过结果；
  9. **签发业务 Token**：Stone 向 Chrome 插件签发带过期时间的受限业务 Token；
    > **安全约束**：插件端全流程仅持有受限业务 Token，不直接接触或持久化存储企业主账号等高危敏感凭据。
- **阶段二：账号切换与环境校验（双路径分支）**：
  - 用户或 Agent 在 Chrome 插件端选择目标操作：**切回本人账号** 或 **切换测试账号**。
  - **路径 A（切回本人账号 · 飞书静默无感复用）**：
    1. Chrome 插件控制浏览器当前标签页跳转至 Coze 页面，并在 URL Query 中显式携带 `prompt=none` 参数；
    2. Coze 宿主页面识别到该参数后，在前端直接静默复用宿主环境中当前活跃的飞书 SSO 登录态；
    3. 页面静默鉴权完成，无感恢复为开发者本人账号身份，全程无需二次输入账号密码。
  - **路径 B（切换测试账号 · UID 换取 Session 与 Cookie 热注入）**：
    1. 用户或 Agent 在插件列表中选择目标测试账号；
    2. Chrome 插件读取 Coze 页面当前已登录账号信息进行前置判断：
      - **分支 1（已是目标账号）**：若当前环境已处于目标测试账号下，插件直接提示操作完成，终止后续冗余网络请求；
      - **分支 2（非目标账号，执行 Cookie 换绑）**：
      1. **请求目标 Session**：Chrome 插件携带有效业务 Token，向 Stone 前端请求目标测试账号的 Session；
      2. **UID 换取 Session**：Stone 前端调用内部 Session 服务，凭借目标测试账号的 UID 换取合法可用的 Session 数据；
      3. **返回 Session 数据**：Session 服务生成有效 Session 并返回给 Stone 前端；
      4. **下发凭证**：Stone 前端将 Session 凭证回传给 Chrome 插件；
      5. **替换目标 Cookie**：Chrome 插件调用浏览器底层 `chrome.cookies` API，将 Coze 当前域名的 Session Cookie 原地原子替换为目标账号凭证；
      6. **页面刷新与三要素校验**：Chrome 插件触发 Coze 页面局部刷新，重新加载并严格校验 **当前账号、所属企业主体与权限套餐**：
        - **[校验一致]**：环境与权限矩阵完全匹配，提示 **「✅ 切换成功（耗时 &lt;10s）」**；
        - **[不一致 / Session 失效]**：若环境未对齐或凭证异常，提示 **「❌ 切换失败，提示重新授权」**。

### 2.5 通用 AI 工程化：ProfilePilot

#### 背景

开发自测离不开 Agent 操作浏览器。当时我评测了当时市面上比较流行的六款开源浏览器自动化工具，发现它们都未能解决以下三个痛点：

1. **人机干扰**：开发者与 Agent 共用 Chrome 时，会争抢窗口和焦点。
2. **多 Agent 冲突**：多个 Agent 同时操作 Chrome 时，会互相干扰。
3. **Profile 复用困难**：难以复制出保留原有登录态和插件的 Chrome Profile。

所以研发了这么一个工具：支持多 Agent并行操作浏览器、不抢占前台Tab、Profile可复制、人与Agent不冲突、支持为不同Profile配置不同代理

- **agent-browser**：无明显功能上的能力不足（原生支持 CDP 调试、网络层 Route/Mock 拦截、扩展特权页访问与登录态跨机持久化移植）；
- **playwright-cli**：无明显功能上的能力不足（原生全功能支持浏览器操作、网络层 Route 拦截、登录态存储恢复与 CDP 调试）；
- **Chrome DevTools MCP**：缺乏协议层网络拦截与 Mock 原语（无原生 Route API，只能在 JS 执行层做脚本降级拦截），且强绑定本地特定 `userDataDir`，登录态与会话状态无法跨机导出与移植；
- **bb-browser**：无法访问 `chrome://` 等浏览器特权页与扩展配置页，原生缺乏网络层 Route/Mock 拦截原语，且自身不支持登录态的保存与导出恢复（无 state save/load，无法持久化产出状态）；
- **@chrome（Codex 插件）**：受宿主安全策略收口，进不了特权页与扩展 options 设置页，缺乏可靠的运行时网络 Route，且无法显式证明与绑定指定 CDP 端口（仅限默认 Profile）；
- **@browser（Codex 内置）**：作为 in-app browser 完全无法继承系统浏览器的真实登录态（免登硬前提不满足），缺乏底层调试与诊断面，不支持文件上传与网络拦截。

#### ProfilePilot 多 Agent 调度与受控 CDP 通信时序解析


- **完整交互时序链路**：
  1. **环境凭证注入**：环境层在子 Shell 启动时自动注入环境变量 `AGENT_BROWSER_SESSION=cc-xxx`，Agent 零感知无需手动指定会话 ID；
  2. **Agent 发起命令**：Agent 在终端执行 `agent-browser --cdp 9223 open ...`（命令行无需显式携带 `--session` 参数）；
  3. **本地参数解析**：Wrapper 拦截命令，提取出环境变量中的 `session=cc-xxx` 与请求的目标端口 `requestedPort=9223`；
  4. **向 Gateway 申领租约**：Wrapper 调用 `acquire(requestedPort=9223, session, autoSwitch=true)`；
  5. **Profile 匹配与排他决策**：Gateway 查询所有 Profile 实时状态与候选备用配置，进入排他判定：
    - **分支 1 [目标 Profile 空闲]**：Gateway 原地原子绑定 `9223 ↔ cc-xxx`；
    - **分支 2 [目标 Profile 被占用，且有可用候选]**：Gateway 自动无缝切换并原子绑定空闲候选 Profile（无需打断用户弹窗确认）；
    - **分支 3 [目标 Profile 被占用，且无可用候选]**：Gateway 返回 `PROFILE_ALREADY_IN_USE` 错误阻断执行，防止多个 Agent 抢占损坏同一浏览器上下文。
  6. **按需以管道模式拉起（选中的 Profile 未启动时）**：Gateway 本地 spawn 启动 Chrome 进程，显式传入 `--remote-debugging-pipe` 进行进程级独占通信（机器对外无开放明文调试端口，防外部偷窥与篡改）；
  7. **下发 Ticket 与连接凭据**：Gateway 建立租约后，向 Wrapper 返回 `chosenProfile`、一次性高防 Ticket 与专属长连接 `wsUrl`；
  8. **Daemon 连接握手**：Wrapper 启动或复用后台 Daemon 进程；Daemon 携带 Ticket 向 Gateway 发起 WebSocket 握手；Gateway 校验 Ticket 的数字签名、有效期与防重放标识；
  9. **受控 CDP 消息转发循环（每条 CDP 指令）**：
    - Wrapper 将具体执行指令交给 Daemon；
    - Daemon 向 Gateway 发送原始 CDP 请求报文；
    - Gateway 严格核验该连接的 Session 控制权与当前控制代次（Generation 状态机）；
    - 校验通过后，Gateway 通过专用管道（Dedicated Pipe）向真实 Chrome 实例安全转发指令并返回结果。
  10. **人工接管与恢复机制（Park / Resume）**：
    - **用户接管**：触发 `park`，系统保持底层 WebSocket 长连不断，暂停并拦截 Agent 后续发来的操作，同时在内存中暂存浏览器推送事件；
      - **交还控制**：人工处理完成后触发 `resume`，唤醒 Agent 并要求其重新截取快照（DOM/Accessibility Tree），从最新状态无缝继续执行。
  11. **任务收尾与租约释放**：
    - **分支 1 [正常完成]**：Agent 执行 `agent-browser profilepilot complete`；
      - **分支 2 [中途放弃]**：Agent 执行 `agent-browser profilepilot release`；
      - Wrapper 最终通知 Gateway 销毁本次会话并释放目标 Profile 租约（供下一任务借调），随后安全结束 Daemon 进程。


#### ProfilePilot 技术架构解析（架构文字版）

##### 一、 Agent 协同控制面 (Control Plane)

> 核心定位：实现无感透明拦截、独占租约分发、受控 CDP 指令管道及运行时人机无缝协作。

1. **第 1 层：wrapper层**
  - **调用端支持**：广泛兼容外部 Agent 与主流测试框架，包括 Claude Code CLI、Codex CLI、Jest、Playwright、Puppeteer 以及各类 E2E 自动化测试脚本；
  - **环境变量注入**：在系统环境层（`~/.zshenv` 等）自动静默注入环境变量 `AGENT_BROWSER_SESSION=cc-xxx`，使外部 Agent 具备原生零感知调用能力，命令行无需手动显式添加 `--session`；
  - **智能命令包装 (Wrapper)**：CLI 包装层拦截所有原始命令，提取会话特征，自动向 Gateway 申请独占租约并换取一次性安全凭证（Ticket）。
2. **第 2 层：Browser Gateway 控制中枢 (租约权威、安全鉴权与受控 CDP 路由核心)**
  - **❶ 租约与并发管理中枢 (Lease &amp; Concurrency Authority)**：
    - **端口与 Session 原子独占绑定**：每个已启动 Profile 端口同一时刻仅承载一个 Agent 独占租约，严格保障上下文独立；
    - **候选池自动切流**：当目标 Profile 处于占用状态时，Gateway 自动调度候选空闲 Profile，杜绝命令因端口冲突而报错抛出；
    - **抢占互斥保护**：从根本上解决多 Agent 或开发者在同一浏览器窗口争抢焦点与键鼠输入的冲突难题。
  - **❷ 安全鉴权与票据引擎 (Ticket &amp; Security Engine)**：
    - **HMAC-SHA256 一次性票据 (Ticket)**：每次建立 CDP 连接前必须由 Gateway 进行高强度签名签发，防止伪造与越权访问；
    - **15 秒短 TTL 与防重放保护**：Ticket 仅允许在极短握手窗口内消费一次，消费即作废，防止调试链接泄露导致重放攻击；
    - **控制代次锁 (Generation Guard)**：每次接管或租约流转均单调递增代次计数，精准阻断网络滞后或失效长连接的幽灵指令穿透。
  - **❸ 受控 CDP 管道与策略代理 (Policy &amp; Dedicated Pipe Proxy)**：
    - **长连事件缓冲与转发**：Agent 驱动通过独立 WebSocket 接入，经 Gateway 安全校验后通过专用管道（Dedicated Pipe）单向安全转发至浏览器。
  - **❹ 会话追踪与人机接管状态机 (Session Tailer &amp; Takeover State Machine)**：
    - **会话日志增量 Tailer**：实时监听 Claude `.jsonl` 与 Codex `rollout-*.jsonl` 增量日志，毫秒级提取自然语言动作与进度状态；
    - **四态状态机流转**：定义 `active`（正常执行） ⇄ `parked`（挂起缓冲） ⇄ `takenOver`（彻底接管） ⇄ `resumed`（交还执行）的严密生命周期；
    - **Park 挂起协同**：当开发者需介入微调页面时保持 WebSocket 长连接，将指令事件排队暂存，交还时唤醒 Agent 重新获取页面最新快照；
    - **Takeover 强接管**：一键优雅终止 Agent 驱动 daemon 进程，目标 Chrome 窗口保持开启不关闭，实现向人类开发者的无缝转交。
3. **第 3 层：页面级人机协同注入 (In-Page Agent Overlay)**
  - **CDP 原生静默注入**：通过底层 `Page.addScriptToEvaluateOnNewDocument` 注入悬浮控制条，跨页面导航持久存在，无需用户手动安装任何 Chrome 扩展；
  - **Closed Shadow DOM 隔离**：组件样式与 DOM 树完全封装于 closed 容器内，彻底杜绝宿主网页自身的全局 CSS/JS 干扰状态条渲染；
  - `**aria-hidden="true"` 降噪设计**：阻止 Agent 的 Accessibility 辅助功能快照将状态条误扫为正文内容，终结 Agent 与状态条自身死循环自交互；
  - **实时进度与意图流显现**：实时展示当前主会话 Agent 名称、正在执行的动作（如“正在填写验证码”）与已完成步骤进度（如 `2/5`）；
  - **双击二次确认接管**：提供「暂停」与「接管」快捷交互，内建 3 秒防误触二次确认逻辑，通过 `Runtime.addBinding` 双向可靠上报控制信号。
4. **第 4 层：运行时受控 Chrome 实例 (Controlled Chrome Runtime &amp; Pipe Driver)**
  - `**--remote-debugging-pipe` 专用独占通道**：采用 Stdio 独占管道替代常规 TCP 调试端口，本机对外不暴露任何可探测网络端口，杜绝公网/内网恶意渗透风险；
  - **多维度探活与端口兜底机制**：集成 `lsof` 进程探测与轻量级 CDP 探活徽章；自动兼容解析 Chrome 144+ 新增的 `DevToolsActivePort` 规范，杜绝 404 失联；
  - **优雅退出 (Graceful Exit) 保留登录态**：关闭或回收 Profile 时优先发送系统级优雅退出指令（macOS `⌘Q` / `SIGTERM`），严禁暴力 kill 进程；留足磁盘 I/O 窗口让 SQLite（`Cookies`）与 LevelDB（`LocalStorage`）正常合并刷盘，根治“一关浏览器就掉登录态”的行业痛点；
  - **外部实例 (External Chrome) 兼容接管**：自动嗅探并以只读方式发现第三方工具启动的 Chromium 实例，提供统一的置顶唤起与安全关闭能力。

##### 二、Profile 数据管理面 (Data Plane)

> 核心定位：管理本地 Chrome 真实数据资产，突破跨平台系统级加密壁垒，实现精准置顶与沙箱生命周期控制。

1. **第 1 层：桌面交互与运维控制台 (Desktop Management Console - Electron Native)**
  - **运维向导与资产调度**：支持一键创建独立测试 Profile 并绑定固定 CDP 调试端口；内置插件迁移向导（自动扫描 Chrome Web Store 与本地已解包扩展）；提供账号会话无损同步（支持差异比对、暂停、取消与一键克隆）。
2. **第 2 层：跨平台窗口前台激活引擎 (按需激活与前台进程验证)**
  - **窗口激活难点**：CDP 请求成功不等于 Windows 已完成前台切换；原生窗口激活受系统前台权限与异步消息处理影响，需要读取实际前台进程确认结果。
  - **三层递进激活策略（Windows）**：
    - **第 1 层：CDP 激活与前台检查**。对带 CDP 的 Profile，先调用 `Page.bringToFront` 请求激活页面，再通过 `GetForegroundWindow` 和 `GetWindowThreadProcessId` 读取前台窗口所属 PID；若属于目标 Profile 的 PID 列表，立即结束。未启用 CDP 时跳过页面激活，直接检查前台进程。
    - **第 2 层：原生激活与等待验证**。仅在尚未确认目标进程位于前台时，按目标 PID 查找窗口并执行 Windows 原生激活，随后短时间轮询前台 PID，确认成功即结束。若使用缓存 PID 的尝试失败，则重新扫描进程信息并重试。
    - **第 3 层：Chrome 单例兜底**。前两层及必要重试仍未确认成功时，按目标 Profile 的数据目录与子目录配置再次执行 Chrome 启动命令，利用单例机制请求现有实例置前，并继续检查前台 PID；仍未确认则返回错误。
  - **空白标签清理**：对 CDP 可访问且握手前已有页面的实例，根据握手前后的 Target ID 差异与空白页 URL 尝试清理新增空白标签。这是启发式识别，无法仅凭这些条件区分握手新增标签与用户同期新开的空白标签。
  - **验证边界**：PID 校验确认的是前台窗口所属进程；同一 Chrome 进程下的多个 Profile 窗口，不能仅靠 PID 精确区分。
3. **第 3 层：跨平台账号会话无损同步 (Account &amp; Session Sync · 破解 OS Crypt 密钥藩篱)**
  - **精细化数据颗粒度与智能缓存清洗 (Data Sanitation)**：
    - **同步的核心资产**：精细化同步 `Cookies (Network/Cookies SQLite)`、`Local Storage (leveldb)`、`Session Storage` 与 `IndexedDB`；
    - **剥离污染源**：严格保留目标 Profile 既有扩展，不盲目复制来源插件以防污染安装记录（保护 `Secure Preferences`）；
    - **清洗巨型脏缓存**：自动过滤数 GB、数万个零碎文件的 `CacheStorage`，根治 Windows 平台启动扫描卡死的严重性能缺陷。
  - **⚡ 操作系统底层加密差异机制 (OS Cryptography Mechanism)**：
    - **🍏 macOS 平台机制（系统级钥匙串集中鉴权 Chrome Safe Storage）**：
      - 凭据加密基于当前 macOS 用户登录会话统一的 `Keychain` 钥匙串项，解密不严格限定物理文件路径；
      - 原生系统 Profile 拷贝至隔离测试 Profile 后，浏览器依然能正常读取当前用户钥匙串解密 Cookies；
      - **成果**：原生实现从系统默认 Chrome 无缝复制完整登录态至独立测试环境。
    - **🪟 Windows 平台机制（App-Bound Encryption 保护藩篱与 DPAPI 副本突破）**：
      - **Chrome 127+ 应用绑定加密**：主加密密钥存储于 `app_bound_encrypted_key`，由 Windows 提权服务进行调用方二进制校验；
      - **原生系统 Profile 无法直接跨目录复制**：由于密钥强绑定原生默认目录，直接拷贝到自定义目录会导致解密失败（防护搬运设计）；
      - **ProfilePilot 隔离 Profile 间克隆突破**：独立隔离实例采用 DPAPI 密钥（`os_crypt.encrypted_key`）；
      - **成果**：ProfilePilot 在隔离副本间精准提取并原子同步 DPAPI 密钥，**实现隔离测试环境间 100% 完整无损克隆**！
4. **第 4 层：本机存储资产与隔离沙箱 (Storage Sandbox &amp; Disposable Clean-Room)**
  - **Chrome 原生 Profile 目录体系**：自动解析 Chrome `Local State`，精准识别日常在用的 `Default` 与 `Profile 1..N` 目录；对主力主账号设置删除保护卡口，禁止误删；
  - **独立测试沙箱 (`--user-data-dir` 物理隔离)**：为每个测试或 Agent Profile 建立独立物理目录，彻底隔绝与日常主力浏览器的数据、缓存与 Cookie 交叉污染；
  - **用完即弃副本池 (Disposable Clean-Room Pool)**：支持一键拉起“一次性克隆”，保留源 Profile 最新登录态；进程退出或窗口关闭后由主进程 Reaper 自动移入废纸篓彻底销毁，确保每次自动化测试均从绝对干净一致的基线开始；
  - **覆盖前自动安全快照 (Pre-sync Snapshot)**：在任何账号同步或扩展覆写执行前，后台自动创建轻量增量备份快照，支持随时秒级一键回滚防意外。

### 2.6 Coze 功能体验成长激励：公共 RPC、任务积分与徽章发放

#### 业务背景与职责范围

Coze 提供云盘、创建 Agent、创建网页等多种能力，但用户可能只使用其中一项。因此设计了成长激励系统：用户首次完成这些体验任务后获得积分，累计达到门槛后解锁徽章，提高功能使用率和用户活跃度。

我负责这项公共能力的全栈需求，**提供统一 RPC，集中处理任务判定、积分累计和徽章发放，徽章能力本身也由我实现。**各业务后端确认操作成功后上报行为，业务前端通过 BFF 查询任务进度、积分和徽章，不需要各自实现奖励规则。

#### 整体架构与业务接入

后端使用 Go，按接入、任务积分、徽章和消息处理划分模块。任务积分模块负责“完成了什么、获得多少积分”，徽章模块负责“应授予什么、当前拥有什么”，运营补发也复用徽章模块。模块共享本地事务，无须拆成多个微服务。

```text
云盘 / Agent / 网页业务后端确认操作成功
              ↓ ReportUserAction RPC
Go：鉴权、参数校验、Redis + Lua 调用方限流
              ↓
MySQL 事务 A：保存行为事件 + 待发送消息（Outbox）
              ↓ 提交后返回“已受理”
Outbox 投递程序 → Kafka → Go 消费者
              ↓
MySQL 事务 B：任务完成 + 积分 + 徽章 + 事件 DONE + 缓存失效 Outbox
              ↓ 提交后推进 Kafka 消费位点

业务前端 → BFF → Go 查询接口 → Redis 缓存 → 未命中时受控查询 MySQL
缓存失效 Outbox → Kafka → 删除对应 Redis 缓存
```

**组件分工。**MySQL 保存事件、积分和授予事实；Kafka 缓冲突发流量并分发异步任务；Redis 缓存用户进度、徽章列表，并保存多实例共享的调用方限流状态。发奖判断以数据库记录为准，不能用缓存中的旧积分决定是否达到门槛。

**接入契约。**`ReportUserAction` 接收稳定的 `event_id`、`user_id`、`action_type`、`object_id` 和操作时间。调用方身份从鉴权上下文获取，积分、徽章和有效期由公共规则决定。同一次操作重试沿用原事件 ID；相同 ID 携带不同语义参数时返回冲突。`ACCEPTED` 只表示事件和发送义务已保存，到账结果通过查询接口确认。业务方负责可靠重试尚未受理的上报，公共服务负责恢复已受理事件。

**规则管理。**当前是少量固定体验任务，任务与奖励规则在 Go 代码或随代码发布的配置中按版本维护。事件受理时绑定 `rule_version`，消费和重试沿用同一版，授予记录保存规则快照。滚动发布先让消费者支持新版本，再切换入口；旧规则保留到积压和重放窗口结束，避免重试时规则发生变化。

#### 任务积分与徽章发放

数据按业务职责分开保存，关键约束由 MySQL 兜底：

**行为事件与 Outbox**：事件以 `(caller_id, event_id)` 唯一，事件记录处理结果，Outbox 记录消息发送义务。

**任务完成与积分流水**：一次性任务以 `(activity_id, user_id, task_id)` 唯一，每条完成记录只对应一笔积分流水。

**用户活动进度**：以 `(activity_id, user_id)` 为主键，保存累计积分和递增版本，也是并发更新时的锁定对象。

**徽章授予记录**：以 `(scope_id, user_id, badge_id)` 唯一，保存本次奖励的规则快照和固定目标到期时间。

**徽章目录与用户徽章**：目录保存名称、图标等定义；用户徽章以 `(user_id, badge_id)` 为主键，保存当前到期时间。

`scope_id` 表示某期活动的一个奖励档位，自动发放和运营补发使用同一资格；仅修改规则版本不会让用户重新获得同一次奖励。

单条事件在一个本地事务内完成处理：

1. **锁定事件与用户进度。**先检查事件状态及投递代次，已完成的直接复用结果；再锁定该用户在本期活动的进度行，读取最新积分。
2. **判定任务并累计积分。**按事件绑定的规则判断是否首次完成，只有新增完成记录时才写积分流水、更新总分。
3. **判断门槛并授予徽章。**按最新积分匹配奖励，首次建立授予记录时才新增或更新用户徽章。
4. **一起提交处理结果。**任务、积分、授予记录、用户徽章、进度版本、缓存失效 Outbox 和事件 DONE 一起提交，成功后才推进 Kafka 消费位点。

这里有三层去重：**同一事件不重复受理、同一任务不重复计分、同一次奖励不重复授予。**例如上传 F1 后 RPC 超时重试，属于事件去重；随后上传 F2，虽然是新事件，也不能再次完成“首次上传”任务。使用数据库唯一约束处理并发，不能只靠“先查再插”或 Redis 锁。

同一用户的进度通过行锁依次更新，不同用户可并发处理。例如已有 80 分，两项任务分别增加 10 和 20 分，最终应为 110 分，避免两个消费者都读取 80 后相互覆盖。所有更新使用同一个事务，保持固定加锁顺序和短事务，并对死锁做有限重试。

徽章采用“至少有效到某个时间”的语义：首次授予时固定 `target_end_at`，原子更新 `expire_at = max(已有到期时间, 本次固定目标到期时间)`。不同活动不会把较长有效期覆盖成较短时间；重试和补发复用原授予记录，不按重试当天重新计算期限。运营补发不需要伪造任务或积分，徽章过期后仍保留奖励判重记录。

#### 缓存、并发与可靠性保障

**缓存一致性。**Redis 按用户缓存任务进度和徽章列表，使用短 TTL 加随机抖动，未命中时查询 MySQL。业务事务同时写入缓存失效 Outbox，提交后删除缓存；删除失败由独立链路重试，不重新加分或发奖。查询可能在删除后回填旧快照，因此普通展示允许短暂延迟；刚完成操作时通过 `GetActionResult` 确认权威结果，进度查询携带 `min_version`，缓存版本不足则从主库读取。热点回源用 Go `singleflight` 合并同进程请求，并设置回源并发上限；Redis 故障时也不能无限打数据库。

**限流与消费并发。**多个 Go 实例按调用方共用 Redis 令牌桶，由短 Lua 脚本原子完成补充、判断和扣减。Redis 故障时使用保守的本地限流和并发上限，降级期间不承诺精确的跨实例配额。Kafka 消息以用户 ID 为 key，同一消费组内分区串行、分区间有界并发，处理能力受分区数和数据库容量约束。重试、补发或分区变化仍可能产生并发，因此数据库行锁和唯一约束始终保留。

**消息恢复。**事件与 Outbox 一起落库，保证受理后即使进程退出，也能继续投递。Kafka 确认接收后才标记发送成功；确认丢失可能重复投递，由消费者幂等处理。消费事务提交前退出则回滚；提交后、位点推进前退出，重读时查到 DONE，直接复用结果。整体采用“至少一次投递 + 业务幂等”，不能在消息刚进入内存时就提交消费位点。

**异常处理与验证。**短暂错误有限退避重试；需要转入延迟重试或死信时，先保存事件状态和对应 Outbox，再推进原消息位点，防止跳过未处理消息。再均衡或停机只提交已完成且仍有分区所有权的位点，历史判重数据保留到约定的重试与重放窗口结束。重点验证重复上报、并发完成任务、提交前后退出、缓存删除失败和重复补发，观察消息积压、到账延迟、锁等待与死信，再调整消费并发，不把理论估算当成实测性能。

## 3. 字节跳动·TikTok 商业化实习

### 3.1 SIM 编辑态大表格性能优化

这个表格服务于 TikTok 商业化 CRM 的季度销售业绩核算。查看态是 79 行 × 12 列的树形表格，约 1000 个单元格；点击进入编辑态后展开至 79 行 × 18 列，达到约 1400 个编辑单元格，并伴随复杂的跨行跨列计算、字段校验与业务联动。

**原始性能瓶颈与排查定位**：

点击“进入编辑”后，编辑态切换耗时高达 **10 秒**；

通过 Chrome Performance 面板、React DevTools Profiler 以及控制变量的替换实验逐步定位根因：

1. **全量 Form.Item 注册与同步渲染瓶颈**：原方案在每个编辑单元格内都包裹了类似 Ant Design 的 `Form.Item`。点击编辑瞬间，1400 个表单项在同一个宏任务中同时实例化、向 Form 实例注册字段与校验规则、初始化受控组件并挂载，导致浏览器主线程被长任务（Long Task）彻底占满；
2. **Context 穿透导致全表 1400 单元格连锁重渲染**：初版尝试剥离 Form 后，使用 React Context 管理整表数据与 dispatch。耗时虽然降到了约 5 秒，但用户在任意单元格键入一个字符，Context Provider 的 value 发生引用变更，导致消费该 Context 的 1400 个单元格全部触发重新渲染；且因为 Context 变动直接穿透了 `React.memo`，依然造成严重打字卡顿；

为了在支持多单元格连续修改、批量提交的同时实现极致性能，我设计了**Mutable Ref + 单元格级发布订阅**的架构方案：

- **Ref 维护草稿数据，解耦数据更新与 React 协调机制**：
  - 整张表格的草稿状态（Draft State）统一保存在 Mutable Ref 中，单元格输入时仅同步写入 Ref 内部数据，不触发 React 协调流程（Reconciliation），更新函数引用保持稳定；
  - 统一提交时一次性从 Ref 中提取整表最新快照进行批量业务校验与网络提交，彻底避免单格频繁保存引发的接口风暴与复算弹窗干扰。
- **基于 EventEmitter 的单元格级局部发布订阅**：
  - 每个单元格组件根据其字段唯一标识（`fieldKey`）订阅局部更新事件通道；
  - 输入时仅向事件中心发布对应字段的局部通知，只有当前被编辑的单元格以及确实受该字段联动影响的目标单元格触发 re-render，将更新范围从 1400 格精准收敛至 1~2 格。

```
【原架构：全表 Context 穿透】
单元格输入 -> Context Provider Value 改变 -> 穿透 React.memo -> 1400 个单元格全部 Re-render (输入卡顿 1s)

【优化架构：Ref 草稿 + 单元格发布订阅】
单元格输入 -> 写入 Mutable Ref (无协调) -> EventEmitter 触发 fieldKey 事件 -> 仅当前单元格/受联动格 Re-render (精准 1~2 格更新)
```

**产出成果**：

- 切换编辑态耗时从 **10 秒骤降至 1.8 秒**，整体交互性能**提速约 82%**；
- 彻底消除了单元格输入时的丢帧与打字延迟，达到稳定 60fps 流畅交互；

**核心思考与面试深度追问复盘**：

- **追问 1：为什么 `React.memo` 无法阻断 Context 变化引发的重新渲染？**
`React.memo` 只能通过浅比较拦截由父组件传来的 `props` 变化。当组件内部使用 `useContext` 消费 Context 时，只要 Provider 的 `value` 引用改变，React 就会直接将该组件标记为 dirty 并安排重新渲染，根本不经过 `memo` 的拦截逻辑。只有将状态移出 Context（如使用 Ref）并配合发布订阅，才能真正实现精准的局部更新。
- **追问 2：为什么不直接采用虚拟列表（Virtual List）？**
该核算表格具有树形展开/折叠嵌套结构、动态行高、复杂联动以及通过键盘 Tab 键快速在单元格间连续切格录入的诉求。直接上虚拟列表不仅改造成本与回归风险巨大，还会破坏原生的 Tab 焦点流转、输入框焦点保持以及原生平滑滚动。在 1400 格量级下，通过状态模型细化 + 分页懒加载已经完全达成 1.8 秒的性能要求，是性价比最高的工程权衡。

- **追问 4：为什么不采用 Canvas 渲染这个大表格？**

我考虑过 Canvas，但当时的主要瓶颈是表单项初始化和过大的状态更新范围。通过减少注册开销、按单元格订阅更新，已经达到了性能目标。考虑到现有的树形结构、校验和连续录入交互，继续优化 DOM 方案的改造成本更低。如果后续规模扩大，且性能分析确认瓶颈主要在布局和绘制，再评估虚拟化或 Canvas。

#### 表格卡顿排查流程：从复现到验证根因

**第二步：先用 Chrome Performance 判断时间花在哪一层。**

打开 DevTools 的 Performance 面板，开始录制，只执行一次目标操作，页面稳定后停止。选中这次交互附近的时间区间，观察 Interactions、Main 主线程及底部分析面板。


如果操作发生后，事件处理迟迟没有开始，先检查主线程此前正在执行什么任务；如果 JavaScript 执行占据大部分时间，再沿字段初始化、业务计算、React 渲染和校验继续定位。

如果 `Recalculate Style` 或 `Layout` 耗时高，重点检查 DOM 数量、复杂布局，以及是否反复读取和修改布局。主线程比较空闲但界面持续等待时，则检查请求、定时器、异步流程或人为延迟。垃圾回收频繁且耗时明显时，检查大对象创建、深拷贝和大数组分配。


在 **Bottom-up** 中寻找累计耗时高的函数，在 **Call tree** 中追踪调用来源。区分 Self Time 与 Total Time：父函数总耗时高，可能是其子调用昂贵，并不意味着父函数自身逻辑很慢。先回答“卡在哪一层”，再决定是否需要虚拟滚动等方案。参考 [Chrome Performance 官方说明](https://developer.chrome.com/docs/devtools/performance/reference/)。

**第三步：如果主要耗时在 React，用 React DevTools Profiler 缩小范围。**

分别录制“进入编辑”和“输入一个字符”，检查每次操作产生多少次 commit、哪些组件参与渲染，以及是少数单元格特别昂贵，还是大量无关单元格都执行了一遍。结合组件状态和代码，追踪更新来自 props、Context 还是本地 state。

对这个表格重点验证两个假设：点击编辑是否一次挂载了大量 Form.Item、Input、Select；输入一个字符是否让无关单元格也重新渲染。React 渲染耗时并不包含完整的浏览器布局、绘制和网络等待，不能替代整个交互耗时。参考 [React Profiler 文档](https://react.dev/reference/react/Profiler)。

**第四步：用单变量替换实验验证假设。**

每次只改变一个实验因素，并与相同基线比较；独立实验应回到基线，分阶段累积改造则单独记录，避免混淆收益来源。


**检查编辑器开销**：保留字段和布局，把 Select 换成简单原生输入框。如果明显变快，继续调查重型编辑器的实现或 options 处理。

**检查表单包装层**：保留编辑器，绕开表单包装层并提供最小必要绑定。如果明显变快，继续调查表单注册、校验或绑定链路。

**检查共享状态传播**：让一个单元格只使用本地 state，停止向整表写入。如果明显变快，继续调查共享状态更新及后续传播。

**检查业务计算**：保留共享状态写入，暂时关闭联动与校验。如果明显变快，再分别关闭两者，进一步区分是哪条计算链路导致开销。

**检查挂载规模**：将挂载行数降到原来的约三分之一，观察耗时是否随之明显下降，以判断挂载规模的影响。


一次替换只能缩小嫌疑范围。例如绕开 Form 后变快，可能同时取消了注册、校验和受控绑定，不能立即断言“字段注册就是根因”，还需要继续拆分并结合调用栈验证。

**第五步：找到昂贵工作后，追问为什么执行了这么多次。**

以 `useState + Context` 管理整表草稿的实现为例，可以沿着以下链路检查：

```text
输入字符
→ updateValues 调用 setFormValues
→ FormSelf 重新渲染
→ 创建新的 contextValue
→ 消费该 Context 的单元格重新渲染
```

源码可以解释更新机制，但要判断它是否为主要瓶颈，还需要 Profiler 中的渲染范围、耗时及隔离共享更新后的对照结果。1400 个字段本身不能证明性能一定差；应继续检查是否每格重复转换字典、每次输入遍历整表校验，或全量挂载重型组件的成本过高。

## 4. 星环科技实习

### 4.1 qiankun 微前端基础设施与自研 Vite 接入插件



**技术挑战与底层架构冲突**：

1. **脚本执行模型与原生 ESM 不匹配**：传统 qiankun HTML 入口接入依赖 `import-html-entry` 提取、执行脚本并获取生命周期；Vite 则使用浏览器原生 ESM 加载。普通脚本执行环境不能直接执行含静态 `import/export` 的模块代码，且浏览器模块的导出不会自动成为 qiankun 可识别的应用生命周期；
2. **生产构建与开发接入割裂**：仅将生产产物改为 UMD/IIFE，无法解决开发环境的 ESM 入口接入；当时使用的 Rollup 构建链路也不支持 UMD/IIFE 多 chunk 输出，若强制内联动态导入，会失去原有的按需分包收益；
3. **静态资源寻址错位**：Vite 没有与 Webpack `__webpack_public_path__` 等价的运行时开关。挂载到主应用文档后，未正确处理的 HTML 相对资源地址可能指向主应用；需要区分 HTML、CSS 和 ESM 内部引用各自的解析基准，避免资源 404。

我开发了一个用于接入 qiankun 的 **Vite 插件**，在开发和构建阶段完成入口转换与桥接代码注入，并通过运行时异步生命周期代理，衔接 qiankun 的应用调度与 Vite 的 ESM 加载。插件同时处理资源寻址适配，并落地到项目的主子应用集成中。

- **自研入口转换与异步生命周期桥接**：
  - **入口转换**：通过 Vite 插件对 HTML 入口进行适配，用普通入口脚本中的动态 `import()` 加载子应用 ESM。动态 `import()` 可以在普通脚本中调用，模块及其依赖仍交给浏览器原生加载器处理，保留 ESM 的模块组织与分包能力；
  - **生命周期提前暴露**：桥接脚本先向 qiankun 暴露 `bootstrap`、`mount`、`unmount` 代理函数；调用代理函数时等待子应用模块和真实生命周期就绪，再转发调用参数并返回执行结果，解决“qiankun 获取生命周期”和“ESM 异步加载完成”之间的时序差；
  - **加载与挂载分离**：模块加载只准备应用代码和生命周期，真正的 UI 创建放在 `mount` 中，由 qiankun 控制；卸载后再次进入时重新挂载，不能依赖模块顶层代码再次执行；
  - **隔离边界**：桥接负责加载和生命周期适配。浏览器原生加载的 ESM 不会自动进入 qiankun 的 Proxy 沙箱，因此不能将该方案表述为完整的 ESM 沙箱隔离；全局变量访问、跨应用通信及副作用清理需要显式管理。
- **静态资源双轨制寻址策略**：
  - **开发态（`server.origin`）**：配置 Vite 开发服务生成资源 URL 时使用的 origin，并为桥接入口解析出子应用服务地址，解决主应用挂载时的资源寻址错位；跨域请求还需要配套服务端 CORS 配置；
  - **生产态（`base`）**：通过 CI/CD 构建流水线注入对应的 `base` 路径（结合 CDN 地址），保证静态资源在多环境部署时拥有绝对可信的公共前缀；
  - **特殊资源兜底**：针对项目中存在寻址问题的图片资源，补充针对性的 Vite 转换逻辑，将适合内联的资源转为 base64，减少对文档路径的依赖。
- **主子路由联动与内存泄漏防护**：
  - 规范主子应用路由前缀契约，主应用基于路径前缀分发子应用，子应用配置对齐的 `basename`；通过自定义事件同步浏览器前进/后退历史；
  - 在子应用 `unmount` 生命周期中，严格执行卸载清理：解绑全局事件监听器、清理未完成的定时器与网络请求，并移除 DOM 容器残留，防止跨应用内存泄露。

```
【主基座与 Vite 子应用加载流】
qiankun (import-html-entry) 
  -> 自研 Vite 插件转换 HTML 入口，生成动态 import 加载脚本
  -> 同步暴露代理生命周期，等待 ESM 加载与真实生命周期就绪
  -> 转发 bootstrap / mount / unmount 调用
  -> 开发态: server.origin 定位本地端口; 生产态: base 统一公共前缀
  -> 独立挂载容器 + 路由联动 (basename) + unmount 深度资源卸载
```

**核心思考与面试深度追问复盘**：

- **追问 1：自研插件最核心的实现是什么？**

核心是“入口转换 + 异步生命周期桥接”：普通入口脚本同步提供 qiankun 所需的代理生命周期，浏览器通过动态 `import()` 加载 ESM；代理函数等待真实生命周期就绪后再转发调用。这样既满足 qiankun 的调度协议，也保留 Vite 的模块加载方式。


- **追问 2：这种方案解决了沙箱和 HMR 的所有问题吗？**

没有。ESM 加载桥接不等于全局对象隔离，模块中的原生 `window` 访问仍需约束。开发服务可接入也不等于框架 HMR 已完整兼容，Vite client、React Refresh 等注入脚本以及 HMR WebSocket 地址都需要针对实际技术栈验证。介绍成果时，应区分“支持开发态接入”和“已验证的热更新能力”。

- **追问 3：工程化时还需要关注哪些边界？**

模块通常会被缓存，因此重复挂载不能依赖顶层初始化再次运行；应用应在 `mount` 中创建 UI，在 `unmount` 中释放资源。加载失败需要传递到生命周期调用方，采用注册式桥接时还要防止注册失败造成 Promise 永久等待。生产入口需要解析真实的带 hash 文件名；若采用直接导出形式，要确保构建保留生命周期导出。多个应用的生命周期与注册状态应按稳定应用标识区分，避免相互覆盖。

### 5.1 Agent Snapshots：Codex / Claude Code 本地会话知识库

Agent Snapshots 是一个的 AI Coding 会话资产管理器与工作记忆入口，将散落在本机各处的异构 JSONL 日志转换为可快速检索、并能随时回到原会话继续工作的个人知识库。

**背景与痛点**：

日常会使用多个Agent，本地积累了大量高价值的会话与排错轨迹。但原始日志面临三大痛点：

1. **日志异构与碎片化**：不同 Agent 工具的日志存储路径、事件格式、Token 统计字段各不相同，缺乏统一视角查看和复盘；
3. **无法继续交互**：传统归档工具仅支持静态查看，无法让开发者基于历史会话一键回到当时的终端上下文继续交互。

**核心方案设计与系统架构**：

- **无依赖领域模型层（`agent-session-core`）**：
  - 抽离出零运行时依赖的独立包，统一将 Codex 和 Claude Code 的日志文件归一化为标准化时间线（包含 message、tool call、tool result、token usage、compaction 等结构化事件）；
- **双层搜索与本地语义检索（Local-first）**：
  - **全文关键词搜索**：基于 SQLite FTS5 trigram 分词建立本地文档索引，毫秒级响应中文模糊关键词与代码错误堆栈检索；
  - **本地向量语义搜索**：将长会话按 chunk 切分，调用本地运行的 Ollama 模型生成 embedding，使用余弦相似度计算匹配度；
- **可逆续接的开发闭环（Session 恢复）**：
  - 归一化持久化记录会话的 engine、session ID 以及工作目录（cwd）；
  - 触发“继续会话”时，优先检测系统内是否已有对应的活动终端；若有则平滑切换，若无则在对应的 cwd 目录自动拉起 `codex resume <id>` 或 `claude --resume <id>`，让历史会话重新接驳至生产力。

#### 5.1.1 面向调试历史的本地 RAG（2026-09-11）

**项目要解决的问题**：用户记得自己以前解决过某个问题，但找不到当时的有效方案。Agent 会话里同时存在用户问题、助手猜测、失败命令、测试输出和最终修复。如果只取语义最相似的一小段，就容易把“尝试过”误当成“验证有效”。

目前已实现查看器搜索中的 **“问历史”** 模式：选择全部项目或当前项目，输入问题后显式提问，返回答案、原文证据卡和会话入口。索引未完成、模型缺失、证据不足、请求取消等状态均有反馈。

**方案**：

> 我在 Agent Snapshots 中实现了一个针对编程 Agent 历史会话的本地 RAG 功能。这个场景的难点是调试记录中有大量失败尝试，语义相关不代表方案有效。
>
> 我按用户轮次组织父块，再拆成小片段做关键词和向量召回，用 RRF 融合排名。命中之后会补齐所在轮次和相邻后续反馈，保留失败、执行与验证的上下文，再生成带引用的答案。工程上做了 SQLite 持久化、按内容哈希复用向量、变更和删除处理，以及取消请求和模型不可用时的降级。
>
> 我还建立了可复现的合成回归集，对关键词、向量、混合检索，以及只给子块和扩展上下文做了对照。真实模型测试让我发现，引用合法并不代表答案正确，因此我把检索指标与生成质量分开评估，保留失败样例，也没有把合成数据的结果宣称成真实业务准确率。

**实际架构与实现细节**：

```text
本地 JSONL → 现有 Codex / Claude 解析适配器 → 脱敏
  → 用户轮次父块 + 1200 字符子块（150 字符重叠）
  → SQLite：会话、父块、子块、FTS、向量缓存
  → BM25 关键词召回 + Ollama 向量余弦召回
  → RRF 融合 → 候选证据筛选
  → 补齐当前父块和下一父块 → 去重与上下文预算
  → Ollama 结构化生成 → 引用编号校验
  → 答案、可展开证据、打开原会话
```

**混合查询与排名融合**：中文描述和错误码经常出现在同一个问题中，因此使用 `Intl.Segmenter` 做中文分词，并提取代码标识符，分别进行关键词和向量召回。两路分数量纲不同，采用 `RRF(d) = Σ 1/(60 + rank(d))` 融合排名，每路最多 40 个候选。当前尚未加入 Cross-encoder 重排，相似度分数也不能解释为正确概率。

**完整覆盖会话与修复反馈**：新建完整片段索引，不沿用旧语义索引每会话前 8 个片段的上限，避免漏掉会话末尾的修复；首次索引分批建立，未覆盖部分会明确提示。检索时先命中小片段，再补齐父块和下一轮反馈，提示词区分建议、声称成功、工具验证及后续否定，减少把失败尝试当成有效方案的问题。当前没有专门训练的结果分类器，不能保证消除误判。

**上下文去重与预算**：父块去重后，每个会话最多保留 2 个证据，总计最多 4 个；按 UTF-8 JSON 字节预算控制内容长度，保留头尾并标明省略。字节预算是保守控制，长上下文仍可能缺失关键中间步骤。

**持久化与增量更新**：使用 SQLite 持久化，主日志路径、文件修改时间、大小等指纹触发更新，内容哈希用于复用未变片段的向量。同名模型原地替换时应重建向量索引；独立子 Agent 文件的单独变化仍需进一步完善跟踪。

**过期索引与删除处理**：变更通过事务替换，尚未成功更新的旧记录不参与检索，删除会话时清理关联记录和孤立向量。同步由请求驱动，尚未接入独立 RAG Worker 持续同步。

**运行时与本机资源限制**：Node 运行时没有 FTS5 时，自动降级为相同分词上的 BM25 扫描，但不能宣称扫描性能等同于 FTS 倒排索引。模型默认使用 `qwen3-embedding:0.6b` 和 `qwen3:4b`，生成上下文为 8192，按请求卸载模型以释放内存；代价是增加模型加载耗时，也可以配置驻留来换取速度。

**引用和展示校验**：要求模型结构化输出，每个结论必须带存在的引用编号，文本以纯文本渲染，避免直接执行生成的 HTML。校验编号存在，并不等于校验了原文与结论的语义支持关系。

**取消与并发控制**：通过 AbortController 向下传递取消，用请求序号阻止旧响应回写，单实例并发冲突返回 409。当前是单进程 RAG 请求互斥，不是分布式任务调度。


#### 5.1.2 RAG 的评测口径与面试追问

**当前评测集**：10 个手工编写的合成调试会话，每个有失败尝试和最终验证；40 个可回答问题，加 10 个语料中没有答案的问题，共 50 题。它是开发回归集，尚不是经过人工标注的真实用户历史测试集。生成抽样覆盖多个场景，包含 8 个可回答问题和 4 个无答案问题。

以下指标需要分开理解：

- **Recall@5 / MRR@5**：前五个不同会话能否找到目标会话、目标排位如何。不能证明找到了正确解决方案。
- **正确方案文本覆盖率**：送入上下文的证据是否包含标注方案的原文。这是自动代理指标，不能等同于模型答案正确率。
- **引用编号合法性**：服务端能确定编号是否存在；“原文是否支持这句话”仍需要人工核对。
- **无答案拒答**：分别记录模型主动拒答、没有召回证据，以及空结论被校验层拦下。系统拒绝输出不等于模型自己识别了所有未知问题。
- **延迟**：分别记录索引同步、检索、生成以及总耗时；模型按请求卸载时，冷加载也是用户实际需要等待的成本。

**2026-09-11 实际运行结果**（50 题合成开发回归集，40 题用于召回与方案覆盖指标）：

**关键词检索**：会话 Recall@5 为 97.5%（39/40），MRR@5 为 0.9208；子块包含正确方案原文的比例为 27.5%，扩展上下文后的比例为 97.5%；检索 P95 约 3.2 ms。

**向量检索**：会话 Recall@5 为 100%（40/40），MRR@5 为 0.9750；子块包含正确方案原文的比例为 32.5%，扩展上下文后的比例为 100%；检索 P95 约 2.80 s。

**混合检索**：会话 Recall@5 为 100%（40/40），MRR@5 为 0.9750；子块包含正确方案原文的比例为 35.0%，扩展上下文后的比例为 97.5%；检索 P95 约 2.80 s。

这里最值得讲的是：在这套合成语料中，相同混合检索下，只给子块时正确方案文本覆盖为 14/40，扩展上下文后为 39/40。这个结果说明补齐调试过程有价值；它不是“答案准确率提升到 97.5%”。纯向量的方案文本覆盖还高于混合方案，因此也不能宣称混合检索在所有指标上都更好。

实际运行环境是 Windows、Node v22.14.0，关键词使用 `bm25-scan` 降级后端；向量模型为 `qwen3-embedding:0.6b`，回答模型为 `qwen3:4b`，默认按请求卸载。上述 P95 包含相应的模型加载成本，是本机单次观察，不是稳定的生产 SLA。

12 道抽样问题的系统流程均完成，没有模型调用或输出结构错误。其中 8 道可回答题调用了生成模型；4 道无答案题均因没有通过筛选的证据而在生成前拒答，**不能据此声称模型本身的拒答准确率为 100%**。抽样生成阶段 P95 约 6.97 秒，不包含前面的检索与索引同步。

**仍然存在的失败案例**：`index-1` 的答案同时给出“新增会话后测试通过”和“索引更新延迟问题未解决”，说明模型仍可能混淆时间顺序；`vector-1` 在回答向量模型问题时附带了其他问题的修复，说明相关性控制仍不充分。两者引用编号都合法，这也是不能把“有引用”当成“回答正确”的直接证据。

原始结果在 Agent Snapshots 仓库的 `docs/evaluations/rag-2026-09-11.json`，包含逐题答案、引用原文、运行配置和代码哈希。早期小模型失败结果另存于 `rag-baseline-2026-09-11.json`。前后同时调整了模型、候选筛选、分词和上下文策略，不属于单一变量的模型消融；阈值也尚未在独立数据集校准。

工程回归新增 15 项，在命令行 Node 与 Electron 运行时均通过。原有完整测试流程在文件监听的短时序用例处曾失败，该用例单独复测通过；其余已执行检查通过，部署 Bash 测试因本机未安装 Bash 而跳过。应保留这些验证边界，不说成“所有平台全部通过”。

**追问：为什么没直接上一个向量数据库？**

> 我先用 SQLite 保存结构化证据和向量缓存，用分页精确余弦扫描建立个人语料的基线。这样便于检查缓存命中、删除一致性和检索结果。当前复杂度随片段数线性增长；如果规模和 P95 超过目标，再评估 ANN/HNSW，而不是在没有量测时宣称已经支持海量检索。

**追问：RRF 为什么比直接加权分数合适？**

> BM25 分数和向量相似度的范围不同，直接相加需要额外归一化与权重校准。RRF 先融合各路名次，作为简单稳定的基线。但它丢失部分分数间隔信息，也不保证每个数据集都优于单路检索，所以我同时保留三种方式的对照。

**追问：如何避免把失败方案推荐给用户？**

> 我把相邻执行结果和后续反馈补入上下文，并明确区分“尝试”“声称成功”和“工具验证”。实际测试中，小模型仍发生过混淆失败方案和最终方案的情况，所以我做了上下文筛选和模型对照，但不声称已经完全解决。下一步应在独立真实标注集上量测误判率，再决定是否增加结果状态抽取或证据重排。

**追问：带引用是不是就不会幻觉？**

> 不是。引用存在只证明链接有出处，模型仍可能误读原文。我的确定性校验拒绝不存在的编号和无引用结论，语义支持关系则通过保留原文和人工评测来检查。这两个层次要分开讲。

**追问：是不是 token 级流式回答？**

> 目前用 NDJSON 流式返回阶段进度和证据，完整结构化答案通过校验后再展示。没有逐 token 展示未经校验的答案，这是为了让界面只展示已经通过引用结构检查的结论。

**可以写在简历上的表述**：

> 为 Agent 会话知识库实现本地 RAG 问答：基于轮次父子块组织历史，融合 BM25 与向量召回，完成上下文扩展、SQLite 增量索引与向量复用、引用校验和请求取消；建立 50 题合成回归集，验证检索与上下文策略，并保留真实模型失败案例进行分析。

尚未完成的能力应作为后续方向：真实会话人工标注集、引用语义支持评测、结果状态分类器、Cross-encoder 重排、ANN 索引和独立 RAG 后台 Worker。不能把这些说成已经交付。

### 5.2 Open Token Board：AI 编码用量与额度平台

Open Token Board 是一个支持自托管的 AI 编码用量与额度分析平台。本机 Agent 读取 Codex、Claude Code、Gemini CLI 等工具的日志，经过归一脱敏后可靠上报，服务端提供多维度排行、额度预警、burn rate 趋势分析与飞书战报。

**核心工程挑战**：

项目最核心的技术难点不是前端图表开发，而是在分布式、不可信网络环境下实现**数据可信**与**并发上报的一致性**：

1. **异构工具的日志口径难以对账**：不同工具的 Token 字段各异（prompt / completion / cache read / cache write），且累计语义与增量语义并存；
2. **弱网重试与重复扫描导致的数据翻倍**：本机 Agent 定时执行，网络抖动重试或多目录软链接扫描极易造成 Token 重复统计；
3. **全量重同步的原子性安全**：用户选择全量重新同步历史时，传统的“先删后插”一旦发生网络中断，将导致线上历史数据永久丢失。

**核心方案设计与系统架构**：

系统划分为 **本机采集 Agent、API 网关鉴权、PostgreSQL 存储、Web 可视化产品** 四层解耦架构：

- **两层幂等设计（彻底杜绝数据翻倍）**：
  - **本地采集层**：通过 checkpoint 水位记录优化扫描性能，按设备号（device）与 inode 去重同一物理文件的多路径引用；
  - **服务端存储层**：基于 `agent-session-core` 为每个事件生成唯一的稳定事件键（`tool:sessionId:eventId`），PostgreSQL 建立强主键约束并配合 `ON CONFLICT DO NOTHING`，从物理层确保任意重试与重复上报都不会导致计数漂移。
- **两层原子性设计（Staging + DB 事务的全量安全替换）**：
  - **网络传输层（三阶段握手）**：`start`（声明预期事件数与文件清单 SHA256 指纹） -&gt; `append`（分批上报暂存至 staging 临时表） -&gt; `commit`（核验总条数与指纹一致性）；
  - **数据库执行层**：仅当数据完整到达且校验通过后，在单一 PostgreSQL 事务中执行“删除旧数据 + 从 staging 批量转移至正式表”，任何一步失败均触发 rollback，旧数据完好无损。
- **用量消耗与订阅额度双轨建模**：
  - **用量模型**：按时间窗口聚合 Token 净消耗量，精确核算真实成本与使用习惯分布；
  - **额度模型**：独立捕捉订阅的时间窗口剩余比例（如 5 小时滑动窗口或周重置额度），结合实时消耗速率（burn rate）预测耗尽时间点，并在额度偏低时通过飞书机器人提前预警。

```
【四层数据对账与一致性链路】
本机日志 (Codex/Claude Code) 
  -> 本地 agent (inode去重 + agent-session-core归一 + checkpoint)
  -> API 鉴权网关 (GitHub OAuth + 稳定事件键生成 + 数据清洗)
  -> 存储层 (两层幂等 ON CONFLICT + 两层原子性 Staging/事务 + PostgreSQL SQL聚合)
  -> 产品表现层 (用量大屏 / 5小时额度预测 / 飞书群战报与低额度预警)
```

**产出成果**：

- 统一了多种异构 AI 编码工具的统计口径，实现了千万级 Token 的零误差幂等对账；
- 平台长期稳定支撑个人与好友团队的 AI 编码消耗监控，日/周报自动推送至飞书群，有效提升了团队用量规划与额度预警能力。

**核心思考与面试深度追问复盘**：

- **追问 1：既然有了三阶段上传（`start/append/commit`），为什么还需要数据库事务？**
两者解决不同维度的原子性：Staging 解决的是不可靠网络传输期间的数据完整性问题，避免因为网络异常中断导致只写入了部分数据；而数据库事务解决的是版本正式替换瞬间的数据一致性问题，防止在旧数据删除后、新数据尚未完全写入期间出现脏读或数据丢失。

### 5.3 dl-code：Agent Runtime 与四个核心能力

dl-code 是一个本地 Coding Agent Runtime，通过 LangChain 的 `createAgent` 创建 Agent，由底层 LangGraph 执行“请求模型 → 调用工具 → 回传结果 → 继续或结束”的循环。LangChain 提供模型、工具和中间件的组装接口，LangGraph 负责执行过程中的状态传递与流程调度，两者在这里是上下层关系。

项目基于框架接口扩展会话管理与上下文管理，具体分工是：

- **会话管理负责保存和组织整段聊天及任务状态。** 项目的 `AgentSession`、`SessionManager` 管理历史记录、运行状态、取消、保存和恢复；执行时把会话消息交给 LangChain，执行产生的新消息再由项目保存。当前执行链没有配置 LangGraph 的检查点持久化。
- **上下文管理负责决定每次请求让模型看到什么。** 项目的 `ContextManager` 管理 Token 预算、历史压缩、近期消息保留和过长工具输出；通过 LangChain 中间件，在每次请求模型之前整理消息，再交给模型处理。

框架本身也提供会话状态持久化、消息裁剪和摘要等能力；dl-code 当前采用自己的会话存储与上下文策略，并通过框架接口接入。在此基础上，项目还实现长期记忆、Skills、MCP 接入和子 Agent 协同。

**Agent Runtime** 管理一次任务的执行生命周期及各组件的协作：AgentSession 管理运行，CodingAgent 驱动框架循环，事件和日志连接执行、展示与恢复。

**压缩** 处理当前任务不断增长的历史与工具输出，组合使用精确重复读结果清理、增量结构化摘要、近期完整消息和原文归档回读。

**Memory** 管理跨任务复用的偏好、项目事实和经验，以 Markdown 条目保存，配套项目与用户隔离、关键词召回、来源跟踪、版本更新和失效处理。

**多 Agent 协同** 管理子任务、依赖、消息和结果验收，由主 Agent 统筹、只读子 Agent 并行调查，并通过邮箱通信、依赖门禁和显式验收组织协作。

**Skill、MCP、Tool** 分别连接任务知识、能力发现和实际执行，采用 Skill 渐进加载、MCP 工具按需暴露、原始 Schema 校验，以及统一调用预算与执行记录。

#### 1. Agent Runtime：dl-code 从接收任务到完成的完整流程

**Agent Runtime 负责把用户的一次请求，组织成一个能够持续决策、执行工具、接收反馈，并且可以被中断和恢复的运行过程。** 其中，Agent Loop 是反复进行的“模型决策 → 工具执行 → 结果反馈”；Runtime 还管理循环的启动、上下文、权限、事件、持久化和结束。

**面试口述：**

> dl-code 的 Agent runtime 管理用户请求的完整执行生命周期。它先建立会话和本轮状态，准备规则、历史、环境与工具定义，再请求模型决定下一步。模型提出工具调用后，运行时负责分发、权限检查、执行和结果记录，再把真实结果交回模型，持续循环。执行过程中，它还处理用户追加要求、上下文压缩、错误重试和取消。满足结束条件后保存状态并通知界面，后续通过历史记录恢复上下文，继续任务。

dl-code 的 Runtime 架构围绕这条任务执行链路组织。下面沿着一次任务讲解完整流程，只解释运行行为，不展开函数和代码。

用同一个需求贯穿全程：

> 帮我修复登录后刷新页面会退出登录的问题，并验证修复结果。

##### 第一步：准备会话和执行环境

用户打开 dl-code、进入项目时，运行时先准备任务运行所需的环境：工作目录、模型配置、权限范围、审批策略、工具连接和会话记录。

如果继续旧会话，就恢复之前的历史及上下文状态；如果创建新会话，就建立新的记录。

这里要区分两个时间尺度：

- **会话**承载持续的对话，可以包含用户多次提出的要求。
- **一轮任务执行**从一次用户输入开始，中间可以调用模型和工具很多次。

所以，“修复登录问题”可以只是一条用户消息，却触发几十次模型决策。运行时需要在这些决策之间保留任务目标、约束和已经获得的结果。

##### 第二步：接收请求，建立本轮执行状态

收到需求后，运行时记录用户输入，建立本轮执行的标识、配置和取消信号，并向界面报告任务开始。

之后出现的模型输出、工具调用、权限请求和结束事件，都能归属到这轮执行。这使运行时始终能够回答：现在正在处理哪个请求？有哪些动作正在进行？用户按下停止时，应当停止哪些工作？

##### 第三步：组织模型第一次决策所需的上下文

运行时准备发给模型的信息，主要包括：

- 行为指令、项目约定和环境信息。
- 当前任务、已有对话和之前的工具结果。
- 本次可用工具的说明与参数要求。
- 当前适用的 Skill、插件等补充信息。

**模型只有看到文件内容后，才能据此分析文件。** 进入项目目录并不意味着整个仓库已经自动进入模型上下文。对于这个登录问题，模型通常需要先调用搜索和读取工具，获得请求封装、登录状态管理和初始化逻辑等材料。

运行时还会检查上下文容量；已有历史过长时，可能在首次请求前先进行压缩。

##### 第四步：请求模型，接收它对下一步的决定

模型根据当前上下文，可能先输出一段进度说明：

> 我先检查登录态的保存方式和刷新时的初始化流程。

接着提出工具调用，例如搜索登录状态相关文件。

运行时通过流式响应逐步接收这些内容：文字交给界面展示，工具调用进入执行流程。一份模型响应可以同时包含说明文字和工具调用。

**模型决定下一步想做什么，运行时负责把这个决定变成实际操作。** 模型说“我要检查文件”只是一段说明；产生有效的工具调用并执行后，才真正读取了文件。

##### 第五步：接住工具调用，检查它能否执行

运行时识别工具名称、解析参数，并把调用分派给相应工具。

对于执行命令、修改文件等受控操作，还需要依据当前策略判断：

- 操作是否允许。
- 是否需要审批。
- 应在什么权限和沙箱范围内执行。

需要审批时，相关调用等待审批结果；被拒绝时，拒绝信息会成为工具结果，让模型知道这个动作没有执行。

权限限制有实际的执行机制支撑。模型提出扩大权限，也需要经过策略判断才能生效。

##### 第六步：执行工具，收集真实结果

检查通过后，工具开始操作真实环境。搜索工具返回文件位置，读取工具返回文件内容，编辑工具改变磁盘文件，命令工具返回输出和退出状态。

运行时也负责调度：支持并行的工具可以同时执行，需要串行的工具通过执行门控避免交错。对于长时间运行的命令，工具可以先返回进程标识和已有输出，后续再读取进展。

例如测试还在运行时，“已经获得一部分输出”并不代表测试已经通过。整个过程中，界面通过事件得知工具开始、输出更新以及完成状态。

##### 第七步：把工具结果写回上下文，再次请求模型

工具完成后，运行时将结果与对应调用关联，记录到历史，再组织下一次模型请求。

模型此时才拿到新证据。例如读取文件后，它发现刷新时先进入了未登录状态，而恢复会话的请求尚未完成，于是决定继续检查初始化时序。

这一过程不断重复：

**准备上下文 → 模型决定下一步 → 执行工具 → 记录结果 → 再次请求模型。**

登录任务可能因此走出这样一条路径：

**搜索相关文件 → 阅读初始化逻辑 → 复现问题 → 修改实现 → 运行测试 → 根据失败结果继续修改 → 再次验证。**

这条具体路径随观察结果变化。运行时负责持续推进循环，模型负责根据新证据选择行动。

##### 第八步：每次继续执行时，处理新增输入和上下文容量

循环过程中，用户可能补充：

> 注意，保持现有登录接口不变。

运行时接收这条输入，并在允许的执行边界将它加入上下文，让后续决策纳入新约束。它不会倒回去修改已经完成的操作。

与此同时，读取内容、命令输出和对话不断累积。达到压缩条件后，运行时进行上下文压缩，建立可继续使用的工作上下文，再恢复任务循环。

因此，压缩发生在执行过程中：它改变后续模型看到的历史表示，任务仍然继续。压缩记录也用于之后的会话恢复。

##### 第九步：出现错误或用户停止时，走对应的中断路径

工具执行失败通常会返回失败结果，让模型判断如何处理。例如测试报错后，可以继续定位和修复。

模型请求遇到可重试的传输错误时，运行时按重试规则处理；不可重试的错误或重试耗尽，会进入错误收尾。

用户主动停止时，运行时传播取消信号，中止相关执行和等待，并记录中断状态。

**停止执行不会自动撤销已经发生的修改。** 文件可能已经写入，外部操作也可能已经生效。继续任务时，需要依据真实环境判断剩余工作。

##### 第十步：判断本轮是否真的可以结束

**一次模型响应结束，整轮任务不一定结束。** dl-code 的运行时会检查是否仍需继续，例如：

- 产生了工具调用，需要把结果交给模型。
- 模型响应明确表示还要继续。
- 收到了尚未处理的用户输入。
- 配置的结束检查要求补充工作，并提供了继续执行的信息。

满足继续条件，就再次进入循环；没有后续工作时，才进行正常收尾。

对于登录任务，模型通常在验证后生成最终说明。但运行时的“本轮执行结束”，本身不能证明登录功能正确。修复是否有效，仍由实际测试和页面行为支撑。

##### 第十一步：保存结果，结束本轮，保留后续恢复能力

收尾阶段，运行时记录最终状态、保存执行记录，并向界面发送完成或中断等事件。本轮结束后，会话仍然可以接收下一条请求。过程中的输入、消息与工具结果也持续记录，持久化贯穿执行过程。

用户以后重新打开会话时，dl-code 根据保存的历史、压缩记录和相关上下文重建工作状态，供新一轮执行继续使用。

这种恢复重建的是任务上下文。之前正在运行的命令，不会仅凭聊天记录就恢复到原来执行到一半的位置；对结果不确定的操作，应重新检查现实状态。

后面的四块设计分别接在这条执行链路中：**模型决策前管理上下文压缩和记忆召回；执行过程中协调子 Agent；需要行动时加载 Skill、发现 MCP 工具并执行。**



#### 2. 压缩：长任务怎样继续执行，又不丢掉工作状态

压缩发生在 Runtime 的模型请求前阶段：完整执行历史继续保存，本次工作上下文由预算和任务状态决定。

##### 为什么不能把完整历史一直发给模型

一次登录任务可能读几十个文件，运行多次测试，并经历失败、修正和重新验证。每次工具结果进入历史后，后续请求都携带它们，输入很快就会被日志和旧文件内容占满。更大的上下文窗口只能推迟这个问题，不能自动判断哪些信息还与当前决策有关。

因此需要区分三份状态：**完整历史、模型工作上下文和界面展示。** 完整历史服务于恢复和回查；模型工作上下文是本次推理需要的材料；界面则还包含正在流式输出、尚未形成完整消息的文字。dl-code 用会话历史保存原始消息，`ContextManager` 生成请求视图，`Transcript` 维护终端展示。

##### 市面上的三类代表方案

**滑动窗口与选择性裁剪**：保留近期消息，移除旧消息或已用完的工具结果。它无需额外总结调用，速度快且容易预测；但简单按轮数裁剪可能丢掉早期约束，选择性裁剪也需要明确规则。

**滚动摘要**：将较早的执行过程总结为任务状态，保留近期原文，后续增量更新摘要。它可以用较少空间维持目标和进度；但总结会损失细节，多次总结还可能把猜测变成事实。

**内容外置与按需回读**：将原文放在文件或归档存储中，上下文只放概览与引用。大内容不必常驻，细节仍可找回；代价是模型需要判断何时回读，并增加一次或多次工具调用。

这些方案可以组合。Anthropic 的上下文工程实践同时讨论了 compaction，以及通过文件路径等轻量引用在需要时读取内容的方法；选择压缩策略时，要关注后续任务能否继续，而不只是压缩率。[官方说明](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

例如用户一开始要求“保持现有登录接口不变”，接着出现了大量搜索结果。按最近十轮保留，可能删掉接口约束；滚动摘要则可以保留约束，同时把已完成的调查压成结论。某次失败测试的详细堆栈不必全部进入摘要，但需要保留归档引用，供后续定位问题。

##### dl-code 怎样组织每次请求

处理流程如下：

```text
完整会话历史
  → 清理精确重复的只读结果
  → 大工具输出写入归档，生成引用和预览
  → 统计系统规则、Skills、记忆、消息和当前工具 Schema
  → 必要时增量总结较早消息
  → 组合任务摘要与近期完整消息
  → 检查最终输入预算
  → 请求模型
```

**第一层先做确定性清理。** 对 `read_file`、`grep`、`ls`、`tree` 和编辑器的 `view` 操作，只有工具名、参数及输出文本都完全相同，才将较早的重复结果替换为引用。后一个完整结果仍然保留。内容发生变化、工具报错、写入操作都不按这个规则清理。程序不猜测两段不同输出是否“意思差不多”。

**第二层处理大输出。** 工具输出超过预算时，先成功保存完整内容，再向模型提供归档 ID 和首尾预览。模型通过 `read_context_artifact` 分页读取，原始历史仍然保存原文。归档证明的是当时观察到了什么；修改文件前，仍需读取当前文件状态。

**第三层才进行模型摘要。** 输入预算从模型总窗口中扣除输出预留和安全余量。预算统计包含当前真正暴露的工具定义；仅统计聊天文字，会漏掉大型工具 Schema。默认在可用输入预算的 80% 触发压缩，目标比例默认是 56%，为后续工作留出空间，避免每新增一点内容就再次压缩。实际窗口和预留通过配置匹配模型。

##### 摘要为什么要写成任务交接

dl-code 的摘要包含目标、约束、已完成事项、待办、文件、验证和下一步七类内容。假设正在接入登录，它应该形成这样的状态：

```text
目标：接入登录，保持现有 API 契约。
约束：请求统一通过 requestClient。
已完成：修复凭据配置，增加失败状态展示。
待办：刷新后登录态丢失；初始化竞态是候选原因，尚未验证。
文件：请求封装、会话 store、初始化入口及相关归档。
验证：类型检查通过；浏览器登录流程尚未验证。
下一步：复现刷新问题，检查初始化请求的时序。
```

这份摘要让接手者知道哪些已经完成、哪些只是猜测。“类型检查通过”不会被要求合并成“登录功能验证通过”，候选根因保留未验证状态。

再次压缩时，只处理“已有摘要 + 新增的旧消息”。`contextCheckpoint` 保存摘要覆盖的消息数量和原始前缀哈希，恢复后先验证摘要是否仍对应同一段历史。近期消息按 Token 预算选择，同时保证一条工具调用及其全部结果不会被拆开。

如果摘要格式无效，系统使用明确标记的未验证摘录并保留原文引用；最终仍然超出硬预算就停止本次请求。最新用户要求和活动规则不通过静默删除来让请求勉强发送。

##### 为什么选择这套组合

本地代码任务既有大量可重复的只读材料，也有需要持续保留的目标和约束。确定性清理减少明显重复；摘要保留任务状态；原文引用负责找回细节。三者覆盖的是不同的信息需求。

压缩效果需要结合任务评估：是否保住用户约束、是否重复调查、是否把猜测写成事实、是否能完成剩余工作。项目测试验证预算、原文保留、工具交换边界和重复结果清理；它们验证运行机制，真实模型的总结质量需要另行用实际任务衡量。

#### 3. Memory：跨会话怎样复用知识，并防止旧结论持续误导

Runtime 恢复 Session 时取回同一任务的状态，组织新一轮模型请求时再召回跨任务知识。Memory 负责后一部分。

##### 先区分会话恢复与长期知识

“昨天做到哪里”与“这个项目长期遵循什么约定”是两类信息。

**任务状态**描述当前工作的进度，例如“正在排查某次登录失败，还有两个测试没跑”。它保存到会话和摘要中，继续同一任务时恢复。

**项目记忆**描述项目的长期约定，例如“项目统一通过 requestClient 注入凭据”。新任务涉及鉴权时召回，并核对当前实现。

**用户偏好**记录用户明确表达的工作习惯，例如“先讨论架构再改代码”。它在后续任务中提供参考，仍以用户当前要求为准。

**经验记忆**保存某次排障得到的可复用步骤和证据，相似问题出现时检索，并结合版本重新判断。

LangGraph 将会话内状态归为短期记忆，将跨会话的数据归为长期记忆。文件是否已经落盘，与系统是否具备有选择的记忆召回，是不同的问题。[Memory 概念](https://docs.langchain.com/oss/python/concepts/memory)

##### 市面上的两类代表方案

**文件式记忆**将偏好、项目知识和经验写入 Markdown，使用目录、索引和搜索定位。优点是人和 Agent 都可以查看，容易纠错，也能接入版本管理。难点在于内容不断追加后会出现重复、过时和文件过大，需要拆分、更新和整理。

**结构化记忆库加检索**将知识保存为独立记录，通过用户、项目、类型、时间等字段过滤，再使用关键词、向量或混合检索召回。它适合数据量较大、多用户或跨项目应用；代价是需要管理存储、索引、召回质量和一致性。向量搜索能够找到表达不同但语义接近的内容，精确标识符、文件名和错误码则通常也需要关键词检索配合。

两种方案并不冲突。文件可以作为可读的内容载体，结构化元数据帮助筛选，索引负责检索。选择时要看记忆规模、可审查性和召回需求，而不是先决定必须使用哪种数据库。

##### dl-code 的记忆存储和作用域

dl-code 使用 **带结构化元数据的 Markdown 条目 + 本地关键词召回**。每条记录是一个独立文件，正文保存内容，frontmatter 保存标题、类型、证据状态、来源、标签、创建时间、更新时间及可选过期时间。

```text
数据目录/memory/
  user/
    response-preference.md
  project-<项目真实路径的哈希>/
    authentication-client.md
    build-command.md
```

用户记忆在本机同一用户的数据目录内共享；项目记忆按规范化的真实路径隔离。新会话使用同一路径时可以复用记忆，其他项目不会自动读到这份项目知识。独立 worktree 的路径不同，对应不同项目命名空间，避免直接混用不同工作目录的结论。

例如一条鉴权知识可以包含：

```yaml
id: authentication-client
scope: project
title: 鉴权请求入口
kind: fact
evidence: verified
source: 检查请求封装并运行相关测试后确认
sourceFile: src/network/requestClient.ts
tags: [authentication, requestClient]
```

正文保存具体事实。`sourceFile` 是可选的项目内来源文件；写入时计算内容哈希，之后召回时重新计算。如果文件变化或消失，该记忆会标为 stale，退出自动召回。这样来源变化会直接影响记忆是否继续生效。

##### 写入、更新和失效怎样形成闭环

主 Agent 获得 `search_memory`、`read_memory`、`save_memory` 和 `invalidate_memory` 四个工具；只读子 Agent 只有搜索和读取。

写入由执行模型在任务过程中显式调用工具完成。提示要求先搜索相关记忆，再决定新增还是更新，只保存长期有价值的事实、明确偏好和经验，不把普通工具日志、临时进度或凭据写入长期记忆。保存操作要求提供来源和证据类别。

已有 ID 更新时必须带上 `read_memory` 返回的 `expectedRevision`。如果用户或另一个会话已经修改该文件，旧版本写入会失败，Agent 需要重新读取并协调内容。命名空间写锁串行化写入，临时文件加重命名避免正常写入时暴露半截文件。相同作用域下，规范化后完全相同的内容会被识别为重复条目，要求更新已有记录。

错误结论通过 `invalidate_memory` 记录失效原因，保留可回查的内容，但不再自动注入。过期条目、来源变化条目以及 `hypothesis` 假设条目也不会参与自动召回。

例如早期判断“刷新失败与 Cookie 配置有关”，后来实际验证为初始化竞态，就可以废弃旧条目，更新根因和对应来源。来源哈希检测文件变化；证据标签由 Agent 根据实际调查填写，程序不把一个标签本身当作事实正确性的证明。

##### 每次模型请求怎样召回

请求前按当前任务文字搜索项目和用户记忆，对标题与标签给予更高匹配权重，再结合正文命中和更新时间排序。英文标识符保留关键词，中文采用相邻双字片段匹配。稳定的用户偏好也可进入候选。

默认选取少量结果，按字符预算拼入系统上下文，并纳入总 Token 预算。正文太长时只给出条目身份和来源，模型调用 `read_memory` 获取全文；不会为了塞满上下文而无界注入。更多内容可以通过 `search_memory` 主动检索。

##### 为什么采用本地文件与关键词

dl-code 面向本地代码项目，代码符号、路径、命令和错误码都具有很强的精确匹配价值。文件条目让用户能直接检查模型记住了什么，结构化元数据又能实现范围过滤和生命周期管理，运行时不需要额外启动数据库或调用 embedding 服务。

因此这里选择的是一套小规模、可检查的记忆系统。它按命名空间限制条目数量，并明确使用词法检索；向量数据库是另一种规模和召回需求下的方案。当前设计优先保证记忆可更新、可失效、可追溯，再让 Agent 将召回内容作为有来源的历史材料使用。

#### 4. 多 Agent 协同：如何拆任务、传递证据和验收结果

主 Agent 在运行过程中通过工具发起委派，Runtime 创建独立执行器并管理结果回流。因此多 Agent 协同同时涉及任务分工和执行生命周期。

##### 市面上的三类代表架构

**Supervisor / 主 Agent 委派**：主 Agent 动态拆分任务，子 Agent 返回结果，再由主 Agent 统筹。它适合开放式代码调查、方案比较和可独立分析的模块，比较灵活，但任务拆分与汇总本身需要成本。

**Workflow / DAG**：由程序定义节点与依赖，允许并行分支和条件流转。它适合步骤较稳定的迁移、生成和检查流程，容易观察和控制，但固定流程可能不适合开放式排障。

**Handoff**：当前处理者把控制权和必要状态交给另一个专家，适合多阶段交互，以及不同专家轮流直接处理用户问题。它的职责划分清晰，但需要管理移交状态和返回路径。

Anthropic 将预定义流程与模型动态规划作了区分，并给出了并行和 orchestrator-workers 等模式。[架构模式](https://www.anthropic.com/engineering/building-effective-agents) LangChain 的 [Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents) 与 [Handoffs](https://docs.langchain.com/oss/python/langchain/multi-agent/handoffs) 则分别说明了中心委派与控制权移交。

这里还有一个容易混淆的点：工作流节点不一定是 Agent。执行测试、判断退出码、转换固定数据都可以直接由程序完成；只有需要自主理解、调查和决策的节点才需要模型。

##### dl-code 的分工方式

dl-code 采用 **主 Agent 动态委派 + 程序管理并发、依赖和验收状态**。主 Agent 保有用户目标，负责代码修改与最后集成；子 Agent 负责独立只读调查。

以登录任务为例：

```text
主 Agent：确定范围、检查入口、修改和整合
  ├─ 子 Agent A：分析前端登录状态与初始化逻辑
  └─ 子 Agent B：分析后端鉴权契约与测试要求

A、B 完成 → 主 Agent 检查证据并验收
  → 有依赖的后续分析引用已验收结果
  → 主 Agent 修改代码并执行集成检查
```

每个子 Agent 拥有独立消息历史、Skills 激活状态、邮箱、取消信号和执行状态。创建时传入具体任务、必要背景和验收标准，不默认复制整个父会话。这样子任务既能获得必要约束，也不会携带父会话所有不相关的搜索和思考过程。

默认最多两个子 Agent 同时运行，每个根会话最多创建 32 个子任务；子 Agent 不能继续派生。这些是运行时约束，限制资源使用和委派树规模。

##### 任务说明和结果怎样传递

`spawn_agent` 返回任务 ID 后，主 Agent 可以继续独立工作。一次委派应包含调查目标、范围、必要背景以及期望交付。默认验收描述要求子 Agent 返回发现、准确来源路径、观察到的证据、未解决假设和下一步建议。

主 Agent 通过 `send_message` 补充要求，通过 `wait_agent` 等待结果，通过 `list_agents` 查询状态。消息在模型请求边界消费并持久化；子 Agent 结束后，结果进入父 Agent 邮箱。等待超时只返回当前状态，不自动取消任务。

子 Agent 可以在自己的上下文中读取大量材料，返回时将结论和来源整理给主 Agent。主 Agent 需要针对关键结论检查证据，而不是把“子 Agent 说完成了”直接当成正确性证明。

##### 为什么要分开执行完成和验收通过

一个子 Agent 正常结束，只能说明执行循环结束。它可能返回“找不到文件”，也可能没有覆盖指定范围。

因此 dl-code 将任务状态与验收状态分开。子任务完成后，主 Agent 调用 `review_agent`，给出接受或拒绝的判断及证据说明。依赖任务通过 `depends_on` 指定已有子任务 ID，只有所有依赖都完成且被接受，才能启动；已接受结果和验收说明会作为新任务的显式输入。

```text
子任务 completed
  → 主 Agent 检查来源与交付标准
  → review_agent: accepted / rejected
  → accepted 才允许依赖任务启动
```

依赖只能指向已存在的任务，因此创建关系沿时间向前，不会形成回环。已被后续任务使用的结果被冻结，不能再通过追加任务悄悄改写其语义；修正调查需要建立新任务。这里实现的是带依赖门禁的动态委派，后续步骤由主 Agent 显式发起。

验收记录表达主 Agent 基于证据的判断；编译、测试等确定性检查仍由相应工具执行，不能由验收文字替代。

##### 为什么只读子 Agent 更适合当前分工

多个 Agent 同时写同一个仓库，容易出现文件覆盖、接口不一致和测试时机混乱。独立 worktree 可以隔离文件修改，但最终仍需要接口协调和集成验证；没有 Git 冲突，不代表没有语义冲突。

dl-code 将并行收益主要放在调查阶段：子 Agent 读取和分析，主 Agent 统一修改。子 Agent 的工具集合不包含 shell、编辑器、Todo、MCP、长期记忆写入或委派工具；即使 Skill 提到这些动作，也无法通过不存在的工具执行。它们仍共享进程和文件系统，读权限沿用当前用户，因此这里是工具能力边界。

取消会传播到运行中的模型和支持取消的工具，执行器退出后才释放并发名额。日志记录状态、邮箱和结果；重启后运行中的任务标记为中断，等待显式继续，已完成且已验收的结果仍能回查。

这套选择适合边界清楚的代码调查。小任务由主 Agent 直接完成，避免为很少的工作支付创建、解释背景和汇总的成本；可独立调查的复杂任务再并行拆分。

#### 5. Skill、MCP、Tool：知识如何加载，动作如何可靠执行

这部分连接 Runtime 的两个阶段：模型决策前提供任务知识与可用工具定义，模型产生调用后由程序执行并返回结果。

##### 三者分别负责什么

假设用户要求发布一个预览环境：Agent 需要知道团队的发布流程，能够执行构建，并能查询部署系统的结果。这些需求对应不同层次。

**Tool** 定义可调用的动作、输入和输出，由运行时执行，例如运行构建、查询部署状态。

**MCP** 标准化外部能力的连接、发现与调用，例如把内部部署服务的查询工具接进来。

**Skill** 提供任务知识、步骤、参考材料和配套脚本，例如团队发布流程、环境选择规则和验收步骤。

MCP 的协议能力还包括资源和提示等内容；dl-code 在这里使用的是工具发现与调用链路。[MCP 架构](https://modelcontextprotocol.io/docs/learn/architecture) Skill 可以包含脚本，但加载说明并不会直接执行脚本，需要通过已有执行工具调用。[Skills 设计](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

##### 市面上的能力加载方案

**全量注册并暴露给模型**适合工具和知识较少的情况。模型一次就能看到完整定义，调用路径短。数量增加后，大量描述与 Schema 会占用输入，也可能让模型难以区分功能相近的工具。

**按需发现与加载**先提供目录或搜索入口，找到相关能力后再加载正文或完整定义。它控制常驻上下文，但会增加发现步骤；如果搜索描述不清晰，模型可能找不到已经存在的能力。Anthropic 的 Tool Search 是工具按需发现的一种实践。[官方说明](https://www.anthropic.com/engineering/advanced-tool-use)

**混合方式**让少量高频基础工具常驻，将专项知识与大量外部工具按需暴露。dl-code 选择这一方式：文件读取、搜索、编辑和 shell 是基础能力；Skill 正文与 MCP 工具定义按任务需要进入模型输入。

##### Skill 怎样渐进加载

启动发现阶段只向模型提供 Skill 的名称和描述。命中任务后，模型调用 `load_skill`，系统读取 `SKILL.md` 正文并登记激活状态；参考材料通过 `read_skill_resource` 继续按需读取。任务结束或不再相关时，`unload_skill` 停止后续注入。

激活记录保存名称、来源路径和内容哈希，每次模型请求重新检查。正文变更、文件消失或同名来源替换时，原激活状态停用并提示重新加载。这样会话恢复后不会无提示地换成另一份流程。

资源路径相对 Skill 目录解析，检查路径穿越和符号链接越界。项目目录规则则随访问范围加载：文件工具发现尚未注入的规则时先返回未执行，等下一次请求带上规则后重试。shell 和外部工具的路径范围由模型先调用 `load_project_instructions` 声明。

##### MCP 工具怎样按需进入模型输入

应用初始化 MCP 连接，读取工具目录及完整 Schema，并把执行对象注册给 LangChain；`ToolCatalog` 在每次请求前筛选模型能够看到的定义。这里将“运行时知道怎样执行”与“本轮模型看见哪些工具”分开。

```text
search_tools：按名称和描述搜索，只返回概要，可分页浏览
  → load_tools：激活选中的工具，返回完整 Schema
  → 下一次请求携带该工具定义
  → 模型调用工具
  → unload_tools：移除不再需要的定义
```

默认最多激活八个外部工具。激活范围属于一次执行，新执行重新发现和选择。未激活的外部工具调用会被拒绝；仅搜索或加载定义不会触发远端业务操作。

现有 LangChain 版本要求工具对象预先登记，因此 dl-code 预注册执行能力，再在模型中间件中按激活集合过滤。过滤发生在上下文预算计算之前，预算反映实际发送的工具 Schema。

##### Schema 与传输怎样保持可靠

MCP 工具保留原始 JSON Schema，使用 Ajv 执行校验，避免把 JSON Schema 简化成 Zod 时丢失 `enum`、整数约束、`oneOf` 或本地 `$ref`。错误参数在远端调用前失败，服务端返回的错误也会进入工具失败结果。`format` 当前按注解处理；结构合法之后，业务合法性仍由具体工具和服务检查。

stdio 传输按行处理 JSON-RPC，使用增量 UTF-8 解码器处理跨块中文，通过请求 ID 关联结果，并在完成、失败和取消时清理等待项与计时器。工具目录支持分页，防止重复游标导致无限循环。

HTTP 传输发送 JSON/SSE 的 Accept 声明，处理初始化通知和服务端会话 ID，携带协商后的协议版本，并从 SSE 帧中提取对应请求的结果。请求有超时和取消信号，关闭连接时中止本地等待。远端是否已产生副作用，需要通过实际状态查询判断；停止等待不会自动撤销远端操作。

##### 统一工具执行层怎样工作

工具调用经过统一中间件，记录调用 ID、工具名、开始与结束时间、状态和错误，并随会话持久化。状态包括运行中、完成、失败和结果未知。已知工具错误与非零 shell 退出码会被记录为失败；运行中断后的未完成记录在继续执行前改为未知。

每个 Agent 的一次运行默认最多发起 50 次主模型请求、150 次工具调用；工具层截止时间默认 65 秒，可通过 `runtime` 配置调整。摘要调用另受上下文管理器的分块和预算约束，主循环还受 LangGraph 图步数限制。达到调用预算后阻止继续调用；触发截止时间则取消本次运行，并等待执行器清理。

系统检查同一运行内重复的调用 ID，避免同一调用被再次执行。它不自动重试具有副作用的操作，也不把跨进程恢复视为工具执行事务。恢复时先补充结果未知的记录，让 Agent 检查文件和外部环境，再决定下一步。

超时处理依赖模型和工具响应取消信号。运行时等待执行器退出，避免仅结束等待就释放仍在写入的执行资源。只读子 Agent 的能力由实际工具集合限制，Skill 和 MCP 描述都不能自行扩大这个集合。

##### 为什么这样组织能力层

基础工具常驻，让本地代码工作不必每一步都先搜索能力；Skill 负责团队私有知识和工作流；MCP 负责外部工具接入；统一执行层负责调用过程的可观察性和运行约束。每部分各自维护职责，最终在模型请求前组合成当前任务需要的输入。

以预览发布为例，Agent 先加载发布 Skill，按步骤运行构建，通过发现工具找到部署能力，校验参数后发起调用，再查询目标环境。是否发布完成取决于实际返回状态及验收结果，不能只根据模型输出一句“已完成”判断。

#### 验证与面试表达

本节对应的实现已接入真实 `CodingAgent` / LangChain 执行循环。离线回归覆盖跨会话记忆、项目隔离、更新冲突、来源变化、假设与过期过滤；覆盖工具按需加载后的真实调用、参数校验、调用预算、取消；覆盖子任务依赖与验收恢复，以及上下文原文保留和重复读结果清理。MCP 使用本地 stdio 与 HTTP 服务验证分页、中文分块、会话协商和 SSE。

2026-09-13 本地验证：`npm test` 的 84 项测试通过，TypeScript 构建、OpenTUI 原生检查和 CLI 入口检查通过；ESLint 为零错误、31 项类型风格警告。这些测试使用脚本模型和本地服务，不消耗真实模型 API，也不将机制测试结果等同于真实编码任务成功率。

### 5.4 agent-session-core：AI 编码会话的统一解析与数据模型

`agent-session-core` 是我为本地 AI 编码工具链抽出的共享解析库：读取 Codex、Claude Code 的 JSONL 会话日志，转换为统一事件时间线，再分别生成用量事件和会话快照。它采用零运行时依赖的 ESM JavaScript，配套 TypeScript 类型声明，让 Node CLI 和 TypeScript 应用复用同一套逻辑。

#### 1. 项目背景与整体架构

Agent Snapshots 需要展示对话、工具调用和图片，Open Token Board 需要统计 Token 与成本。两者读取的是同一类会话日志，但如果各自维护解析器，就容易对累计值、缓存、重复消息和模型切换形成不同理解：同一个会话在两个产品里显示出不同数字，修复也需要同步多份代码。

我把这部分抽成 `agent-session-core`，让引擎差异在解析层收口。当前本地 Agent Snapshots 的 `src/sources/asc-adapter.mts` 已调用它生成快照，Open Token Board 的 `packages/token-board-core/src/asc-collector.ts` 已通过适配层消费它的解析结果。

**agent-session-core** 将异构日志转换为统一会话事件，再生成不同数据视图，面试时重点讲字段语义、解析正确性和公共库边界。

**Agent Snapshots** 负责会话检索、展示、分享与知识回查，重点讲产品交互、脱敏和本地 RAG。

**Open Token Board** 负责用量采集、上报与分析，重点讲数据去重、可靠上报和统计口径。

**dl-code** 驱动模型和工具执行任务，重点讲会话运行时、上下文管理、取消与恢复。

这里要区分 `agent-session-core` 和 dl-code 中的 `AgentSession`：前者读取已经产生的日志，后者管理正在执行的会话。整体架构围绕“一次解析，多种投影”展开：

```text
本地 Codex / Claude Code JSONL
  → discovery：发现会话文件、过滤与文件去重
  → parse：选择引擎解析器，逐行读取日志
  → NormalizedSession：会话元信息 + events 时间线
      → toTokenEvents / sessionTokenTotals：用量事件、汇总与成本估算
      → toSnapshot：消息、图片、工具记录与展示所需的快照
  → 各产品的适配层：上报、搜索、渲染和分享
```

`NormalizedSession` 保存引擎、会话 ID、工作目录、模型、时间和标题等元信息；事件按 `kind` 区分 `message`、`tool_call`、`tool_result`、`token_usage`、`compaction`、`web_search` 和 `reasoning`。投影就是从这份共同数据中取出某个消费方需要的结构，不必重新理解原始日志。

“一次解析”指同一个解析结果可以在一次调用流程中被多种投影复用；两个独立应用各自运行时仍可能各读一次文件，当前没有跨进程共享解析缓存。

#### 2. 日志解析与统一数据模型

这里的“引擎”指产生日志的 Codex、Claude Code 等工具，不是它们调用的模型。“引擎解析器”就是专门读懂某一种工具日志格式的代码：`parseCodexSession` 负责 Codex，`parseClaudeSession` 负责 Claude Code。

“解析层”是把原始日志转换成统一会话数据的这一组代码。它先通过 `JSON.parse` 把每行文本变成对象，再理解字段的含义：这是普通消息还是工具结果、用量是累计值还是单次值、记录是否重复，最后生成统一事件。只把 JSON 字符串转成对象，还没有完成这里所说的解析与归一化。

下面以“读取 `src/Login.tsx` 并返回文件内容”为例，展示本项目支持的原始格式。示例省略了无关字段，工具名称和参数仅用于说明结构，不代表所有版本都有同名工具。为方便阅读先展开排版；实际 JSONL 文件里，每个外层对象独占一行。

**Codex：调用与结果由 `payload.type` 区分。**

```json
{
  "type": "response_item",
  "timestamp": "2026-09-12T10:00:01Z",
  "payload": {
    "type": "function_call",
    "name": "read_file",
    "arguments": "{\"file_path\":\"src/Login.tsx\"}",
    "call_id": "call-001"
  }
}
```

```json
{
  "type": "response_item",
  "timestamp": "2026-09-12T10:00:02Z",
  "payload": {
    "type": "function_call_output",
    "call_id": "call-001",
    "output": "文件内容……"
  }
}
```

**Claude Code：调用与结果放在消息的内容块中。**

```json
{
  "type": "assistant",
  "timestamp": "2026-09-12T10:00:01Z",
  "message": {
    "role": "assistant",
    "content": [
      {
        "type": "tool_use",
        "id": "call-001",
        "name": "Read",
        "input": { "file_path": "src/Login.tsx" }
      }
    ]
  }
}
```

```json
{
  "type": "user",
  "timestamp": "2026-09-12T10:00:02Z",
  "message": {
    "role": "user",
    "content": [
      {
        "type": "tool_result",
        "tool_use_id": "call-001",
        "is_error": false,
        "content": "文件内容……"
      }
    ]
  }
}
```

Claude 的 `user` 消息也可以承载交回模型的工具结果，不一定是用户亲自输入的话。因此解析器要检查内容块，不能把所有 `user` 行直接当成人类消息。

**调用类型与名称**：Codex 用 `payload.type = function_call` 标记工具调用，Claude Code 的内容块使用 `type = tool_use`，归一后都是 `kind: "tool_call"`。Codex 的 `payload.name` 与 Claude Code 的 `name` 都映射到统一事件的 `name`，保留原工具名。

**调用参数**：Codex 的 `payload.arguments` 是 JSON 字符串，Claude Code 的 `input` 是对象，统一后放入 `args`，本例采用 JSON 字符串表示。

**调用与结果关联**：Codex 的调用和结果都使用 `payload.call_id`；Claude Code 的调用使用 `id`，结果使用 `tool_use_id`。这些标识统一映射为 `callId`，用于关联同一次工具调用及其结果。

**返回内容与成功状态**：Codex 的 `payload.output` 与 Claude Code 的 `content` 映射到 `outputText`。成功状态统一为 `ok`，其中 Codex 根据输出内容启发式判断，Claude Code 根据 `is_error` 判断。

统一结构不等于消除了所有语义差异。例如 Codex 的失败判定目前依赖输出内容，不能声称与 Claude 的结构化错误标记同样可靠；不同工具的名称和参数结构也仍由原工具决定。

解析结果是一个 `NormalizedSession` 对象，其中的 `events` 按日志顺序收集事件。下面是简化的 Claude 会话示例，省略了部分元信息，文本和数值均为示意：

```js
{
  engine: "claude",
  id: "session-001",
  cwd: "/projects/my-app",
  model: "example-model",
  title: "检查登录按钮",
  events: [
    {
      kind: "message",
      ts: "2026-09-12T10:00:00Z",
      role: "user",
      text: "帮我检查登录按钮为什么不能点击"
    },
    {
      kind: "tool_call",
      ts: "2026-09-12T10:00:01Z",
      name: "Read",
      args: '{"file_path":"src/Login.tsx"}',
      callId: "call-001"
    },
    {
      kind: "tool_result",
      ts: "2026-09-12T10:00:02Z",
      callId: "call-001",
      ok: true,
      outputText: "文件内容……"
    },
    {
      kind: "message",
      ts: "2026-09-12T10:00:04Z",
      role: "assistant",
      text: "按钮处于 disabled 状态，需要检查禁用条件。"
    },
    {
      kind: "token_usage",
      ts: "2026-09-12T10:00:05Z",
      model: "example-model",
      usage: {
        input: 1000,        // 全部输入，已经包含两种缓存
        cached: 600,        // 其中：缓存读取
        cacheCreation: 100, // 其中：缓存创建
        output: 200,
        reasoning: 0
      }
    }
  ]
}
```

`kind` 是事件类型的判别字段，决定后面有哪些数据：消息带 `role` 和 `text`，用量事件带 `usage`，不能假定所有事件都有同一组字段。这里总 Token 是 `1000 + 200 = 1200`，缓存不能再次累加。

`args` 是 arguments 的缩写，表示“调用工具时传了什么参数”。`callId` 是 call ID，表示“这是哪一次调用”，不是 `called`。调用和结果携带相同的 `callId`，就能关联起来；即使多次调用同一个工具，也不需要靠工具名称猜测结果归属。它由原日志提供，缺失时解析器不能凭空保证关联成功。

上层可以直接选择需要的事件，不必再理解两种原始日志的嵌套方式：

```js
const usageEvents = session.events.filter(event => event.kind === "token_usage");
const messages = session.events.filter(event => event.kind === "message");
```

这是投影的基础；完整的 `toTokenEvents` 和 `toSnapshot` 还会做字段映射、汇总或展示处理。这里还需要区分原始日志的存储格式与统一后的内存结构。

JSONL 的每一行都是一个完整、独立的 JSON 值。会话日志一般每行写一个对象，例如：

```text
{"kind":"message","text":"检查登录按钮"}
{"kind":"tool_call","name":"Read"}
{"kind":"tool_result","outputText":"文件内容……"}
```

如果用一个 JSON 数组存同样的内容，则需要外围数组和元素间的逗号：

```json
[
  { "kind": "message", "text": "检查登录按钮" },
  { "kind": "tool_call", "name": "Read" },
  { "kind": "tool_result", "outputText": "文件内容……" }
]
```

JSONL 适合持续产生事件的会话日志：在文件末尾追加一行即可，无需维护 JSON 数组结尾和元素逗号。文件很大时，可以逐行解析，无需先读入整个文件；普通 JSON 也能使用专门的流式解析器，但实现更复杂。

进程突然退出时，最后一行可能不完整，前面完整的行仍能独立解析，但这不等于保证数据已经刷盘。需要实时观察时，也可以持续读取文件新增行，逐条处理新事件。

**本项目统一后的结果既不是 JSONL 文件，也不是 JSON 文本，而是内存中的 JavaScript 对象。** `NormalizedSession` 描述数据结构，JSON / JSONL 描述序列化后的文本格式，两者是不同层面的概念。

```text
磁盘 JSONL
  → 分块读取、逐行 JSON.parse
  → 每行对应的 JavaScript 对象
  → 提取字段、去重、计算用量增量
  → 内存中的 NormalizedSession { 会话元信息, events: [...] }
  → 用量或快照投影
```

消费方需要保存时，可以自行选择格式。下面只是序列化示意，不代表核心解析器默认执行了文件写入：

```js
// 整个会话序列化成一个 JSON 文本
const jsonText = JSON.stringify(session);

// 只将事件序列化为 JSONL 文本
const jsonlText = session.events
  .map(event => JSON.stringify(event))
  .join("\n") + "\n";
```

第二种方式只保存事件，会话 ID、工作目录等外层元信息需要另行保存。当前解析器虽然逐行读取输入，最后仍将事件保存在内存数组中；选择 JSONL 输入，并不自动获得增量缓存、恒定内存或实时监听能力。

**面试口述**：

> 原始日志使用 JSONL，方便持续追加和逐行读取。我的解析层先读懂 Codex 和 Claude Code 各自的字段，再把消息、工具调用、结果和用量归一成内存中的会话事件。比如两边不同的调用标识统一为 callId，参数统一放到 args，调用和结果就能关联起来。上层基于同一份事件生成统计或快照；如果要落盘，再由消费方选择 JSON 或 JSONL。

#### 3. Token 统计：累计重置、缓存口径与去重

Codex 的 `total_token_usage` 是累计快照。正常情况下逐字段计算 `max(0, current - previous)`；当前累计总量小于前一个正数累计总量时，按计数器重置处理，将当前快照整体计入新窗口。

例如累计总量依次为 `300 → 50 → 200`，中间发生了一次重置：

**只取最后一条快照**会得到 200，丢失重置前的窗口。

**普通非负差分**会算出 `300 + 0 + 150 = 450`，丢失重置后的第一笔 50。

**重置感知差分**会算出 `300 + 50 + 150 = 500`，等于两个窗口末值之和 `300 + 200`。

算法集中在 `src/engines/codex-tokens.mjs`。测试除了覆盖首次快照、连续重置、重置后继续累积，还用独立的“各窗口末值求和”算法交叉检查结果，避免测试只是复写实现。`total_tokens` 缺失时会尝试从组成字段重建用于重置判断的总量，避免把缺字段当成零而误判。

这仍是根据日志计数器下降识别重置的规则，不能据此判断每次上下文压缩的完整过程，也不能恢复日志本身没有记录的用量。

Claude 则需要处理消息用量重复的问题：同一条 assistant 消息可能拆成 thinking、text、tool_use 等多行，每行重复携带该消息的用量。解析器以 `(message.id, requestId)` 为组合键，仅第一次生成 `token_usage`，消息与工具事件仍按各行保留。缺少消息 ID 时退回逐行计数，因此去重能力依赖日志提供足够的身份信息。

统一后的 `input` 包含普通输入、缓存读取和缓存创建；`cached` 只表示缓存读取子集，`cacheCreation` 单独保留，`totalTokens = input + output`。这样既能比较完整输入量，也能在成本估算时区分不同缓存计价，避免把缓存字段再次加到总量上。

每条用量事件还保存自己的模型，投影优先使用事件模型，再回退到会话模型，防止会话中途切换模型后把所有调用算到同一个模型上。成本由可替换的价格表估算；未知模型当前返回零估算值，不能把它解释成实际免费，更不能把本地估算当作账单。

#### 4. 大文件处理与公共库边界

日志读取使用同步分块迭代器，以 1 MiB 窗口读取，再逐行交给解析器；`StringDecoder` 处理跨块的 UTF-8 字符，避免把中文切坏。当前解析字节上限为 256 MiB。它减少了整文件读成字符串再 `split` 的额外开销，但事件数组仍保存在内存中，因此不能称为整体恒定内存的流式系统；同步解析也仍会占用调用线程。

`toSnapshot` 通过回调接收 HTML 渲染、文本脱敏和风险检测能力，核心包无需依赖页面框架或 Markdown 渲染器。工具输出默认隐藏，预置内部消息不会作为普通对话展示；图片和工具记录则按快照契约保留。脱敏依赖消费方注入实际实现，单独传 `redact: true` 并不等于已经获得完整的隐私保护。

## 6. AI 使用相关

### 6.1 过度迷信 Spec-Driven，陷入“文档即交付”与上下文污染陷阱

**踩坑**：初期尝试让 AI 生成详尽完备的 PRD、Design Doc 与 Task 拆解，但在高频迭代的真实业务场景下，文档在写完即与实际代码脱节；动辄上千行的冗长文档不仅严重挤占上下文窗口（Context Window），而且人review起来也特别麻烦；

**解决**：转向人机协同轻量闭环，人工前期仅对齐约 80% 的架构边界与模块职责；大任务拆分为独立的子会话（Sub-sessions），主会话把握进度与统筹，子会话专注局部交付；以真实代码库和类型契约为单一事实来源（Single Source of Truth）。

### 6.2 应该用harness约束AI，而不是纯靠prompt

1. **把架构和依赖要求变成自动检查规则。**

   重构前，明确模块依赖关系、接口兼容要求和修改范围，例如：跨模块访问必须通过公开接口、公共组件不能依赖具体业务、禁止新增循环依赖。

   通过 ESLint、依赖检查、类型检查和架构测试落实这些要求。检查失败时，返回具体位置和原因，让 AI 根据反馈修复。同时区分历史问题与新增问题，并审查规则文件的修改，避免 AI 通过关闭检查来绕过约束。

3. **把“已经完成”绑定到可验证的证据。**

   提前定义完成标准：缺陷修复需要验证原问题已消失、相关功能未受影响；功能发布需要确认目标版本已生效、关键路径可正常使用。

   Harness 应记录实际验证结果，使完成结论能够追溯到测试输出或运行状态。没有执行或无法完成的验证，应明确标记为“未验证”，避免 AI 仅凭代码写完、命令执行或平台返回成功就宣布完成。

### 6.3 skill不是越多越好

**我的分类原则**：

1. **模型能力补丁**：几个月之前的模型，跑长任务会遗忘计划、重复调查、上下文压缩之后会丢失进度，所以那时候我搞了个skill，将计划、发现、进展什么的写入文件，然后通过hooks在后续步骤中重新注入，当然现在模型能力增加，压缩几百轮、跑两三天的长任务，我也都测试过，跑的好好的，没啥问题。然后再早之前比如说模型会把lint通过当做构建成功， 看见报错就猜修复方案之类的问题；

2. **公共领域知识**：React、TypeScript、Git 的一般知识通常不值得重复教授，模型的预训练知识已经足够，Skill 还可能冻结过时版本或个人偏好。若要求的是“本团队 React 禁止怎样写”，它就不再是公共知识，而是下一类团队规范。

3. **私域知识、团队规范与个人工作流**：仓库架构边界、内部发布流程、业务术语、测试账号切换方式、个人稳定习惯，以及模型无法自行发现的工具协议，是最值得沉淀的内容。它们的价值不是让模型“更聪明”，而是告诉模型这个环境里无法从公共语料推导出的事实。

4. **确定性能力封装**：可视为第三类中价值最高的子类，例如内部 API 客户端、浏览器控制、固定格式生成器、发布脚本和带 Schema 的数据转换器。此时 Skill 的主要作用不是灌输知识，而是让模型调用经过测试的程序，把概率性的文本生成收敛为可复现执行。

### 6.4 怎么写好一个 Skill

1. **先确认值不值得做成一个Skill，Skill并不是越多越好。** 遇到问题时，看看模型欠缺的知识是不是私域知识、团队规范、个人工作流、确定性的能力封装这种的，这种的才值得做成Skill。

2. **边界明确，让 Agent 知道什么时候该用。** 一个 Skill 围绕一个清晰的任务场景。`description` 要写清楚“能做什么、什么时候用”，包含具体任务对象和触发词，避免“帮助开发”这类过于宽泛的描述。

3. **SKILL.md 保持精简，写清核心流程，何时读取或者调用references，可程序化的固定步骤交给脚本。** 正文写清任务目标、输入与前置条件、关键步骤、验收标准和失败处理；固定规则和参数要具体，需要 Agent 判断的环节保留自由度。固定流程中，输入输出明确、规则稳定且能用程序可靠执行的部分放 `scripts/`，其余由正文指导 Agent 执行。详细资料放 `references/`，模板放 `assets/`；正文说明何时读取或调用，并交代脚本参数、依赖和副作用。

4. **结合人工审查和代表性任务验证，再根据失败案例迭代，比较有无 Skill 的效果，确认它带来了实际改善。** 人工检查指令、脚本和产出质量，通过实际执行验证触发、流程和结果。

### 6.5 为什么会出现 AI 幻觉？如何减少？

#### 出现幻觉的原因

**1. 用户提供的上下文不足，Prompt 不够精确。**

缺少业务背景、依赖版本、完整报错或明确的任务边界时，模型可能按默认假设补全信息。如果模型没有澄清或说明不确定性，而是把这些猜测当作事实输出，就可能产生幻觉。例如，没有提供项目使用的库版本，模型就可能给出当前版本不存在的 API。

**2. 模型的概率性生成不保证事实正确，看起来合理的答案也可能是错的。**

语言模型根据上下文预测后续 Token，某段文字的生成概率高，不等于它在现实中正确的概率高。模型可以生成表达流畅、符合常见模式的回答，却拼出不存在的 API 或未经证实的关系。后训练和核验机制可以提高准确性，但不能保证每条陈述都正确；在证据不足时，模型也可能继续给出看似合理的答案。

**3. RAG 也不能保证可靠：检索质量有限，模型也不一定正确使用证据。**

RAG 可以通过补充外部知识降低幻觉，但检索可能漏掉关键资料，返回不相关、过时或错误的内容。即使找到了正确资料，模型也可能忽略证据、误读条件，或加入资料没有支持的推断。例如，文档写着“企业版支持导出，需要管理员开启”，模型却回答“所有用户都可以直接导出”。因此，检索到资料、回答带有引用，都不能直接证明结论正确，还需要核验资料是否适用，以及证据是否支持具体结论。

#### 减少幻觉的工程方案

**1. 补足上下文，明确任务要求和信息边界。**

提供必要的业务背景、依赖版本、相关代码和完整报错，说明目标、约束与验收标准。信息不足时，让模型先查询或澄清，并区分已知事实和待验证假设，避免自行补全后当成事实。

**2. 用外部证据和工具核验关键结论。**

不能仅凭回答流畅、模型表示确定，就认为结果正确。计算结果通过程序验证，API 用法检查当前版本的文档和实现，构建是否成功查看实际执行结果，功能是否正常通过对应的测试或操作验证。将关键验收条件写成自动化检查，发现错误后根据实际反馈修正；无法核实的内容保留不确定性。

**3. 提高 RAG 的检索质量，并检查回答是否得到证据支持。**

优先使用可信、及时且适用于当前场景的资料，检查检索结果是否相关、完整，必要时补充检索。生成后核对关键结论与原文是否一致，尤其注意版本、适用条件和例外，不能只检查有没有引用。证据不足或互相冲突时，明确说明无法确认，避免强行给出答案。
